# Аудит платежей и доступов

Проверенный исходный код: `cc14551`. Только локальная изолированная среда: настоящий обработчик API с поддельными Telegram/Supabase и SQL-функции миграций в PGlite. Реальных покупок, возвратов, сообщений и записей в production не выполнялось.

## Подтверждённые проблемы

### PAY-1 · P1 · Две отдельные оплаты могут списаться за один доступ

- Места: `supabase/functions/api/index.ts:1218` (pre_checkout проверяет только уже выданный доступ), `supabase/functions/api/index.ts:1244` (каждый новый charge принимается), `supabase/migrations/007_refunds_webhook_url.sql:16` и `:26` (оплата уникальна по charge, доступ по user/course).
- Сценарий: открыть два отдельных счёта одного платного курса; оба pre_checkout приходят до первого successful_payment. Оба получают `ok=true`. Затем Telegram доставляет два разных успешных charge.
- Воспроизведение: `approvals=[true,true]`, два платежа по 500, один `course_access`, ноль вызовов refundStarPayment. Повтор одного charge защищён корректно; ошибка относится к двум разным покупкам одного права доступа.
- SQL-проверка подтверждает, что обе оплаты фиксируются как новые (`duplicate=false`), а право доступа остаётся одно. Это допустимый порядок доставки, а не заявление о выполненной гонке в production.
- Последствия: двойная оплата за один курс, ручной возврат владельцем. Применимо к активным платным курсам и ранее отправленным счетам. Все 28 текущих авторских программ бесплатны, поэтому обычный путь их чтения этот дефект не задействует.
- Исправление: устойчивый серверный purchase intent для пары user/course, защита двух checkout и обязательная компенсация второго успешного списания, если оно всё-таки произошло. Сохранить charge-идемпотентность и корректное восстановление после ошибок refund.

### PAY-2 · P2 · Ручная выдача после покупки теряется при возврате

- Место: `supabase/migrations/20261028090000_core_atomic_operations.sql:28`; цепочка `adminGrant → decideRequest` в `supabase/functions/api/index.ts:942`, удаление доступа при возврате в миграции `20261028090000_core_atomic_operations.sql:66`.
- Сценарий: ученик покупает курс; автор вручную выдаёт ему тот же курс; затем возвращает деньги за покупку, рассчитывая оставить выданный доступ.
- API возвращает 200 на ручную выдачу и подтверждает открытие курса, но `on conflict do nothing` оставляет единственный `source='stars'`. Refund удаляет эту запись. Данные: до refund `['stars']`, после `[]`. Подтверждено и API, и реальными SQL-функциями PGlite.
- Последствия: ученик лишается явно выданного автором доступа. Обратный порядок (ручной доступ → покупка → refund) уже защищён существующими тестами и не является этой ошибкой.
- Исправление: хранить независимые основания доступа либо атомарно переводить существующий платёжный grant в ручной при ручной выдаче. Возврат должен отзывать только право, основанное на соответствующей оплате.

### PAY-3 · P2 · Ошибка сохранения заявки выдаётся за успешную отправку

- Место: `supabase/functions/api/index.ts:746`.
- Сценарий: Supabase возвращает ошибку upsert в `access_requests`.
- Результат изолированной проверки: HTTP 200, `{request:'pending'}`, в таблице заявок ноль записей, администратору сформировано одно уведомление. Ошибка upsert не проверяется.
- Последствия: ученик считает заявку сохранённой, но в списке админки её нет. Одобрение через полученное уведомление может восстановить доступ, однако это не делает ответ интерфейса достоверным.
- Исправление: проверить результат upsert и вернуть ошибку до событий/уведомлений; уведомлять после подтверждённой фиксации, при необходимости через outbox.

### PAY-4 · P2 · Из админки недоступны покупки старше последних 100

- Места: `supabase/functions/api/index.ts:961`, `src/screens/AdminCourses.tsx:37` и список покупок `src/screens/AdminCourses.tsx:161`.
- API жёстко ограничен `limit(100)`, не принимает cursor/offset и не возвращает следующую страницу; интерфейс не предлагает загрузку архива/поиск платежа.
- Воспроизведение: 101 запись в журнале → API возвращает 100, самая старая отсутствует, ответ содержит только `payments`.
- Последствия: после сотни покупок владелец не может найти и вернуть старую покупку штатным интерфейсом. Ручной вызов API по известному ID возможен и не заменяет пользовательский путь.
- Исправление: серверная пагинация, поиск по ученику/charge/дате, явные ошибки загрузки; проверить возврат покупки с первой страницы истории.

## Что подтверждено исправным

- Цена счёта берётся из серверной записи курса, а не из клиентского payload.
- pre_checkout проверяет пользователя, валюту, актуальную цену, опубликованность и уже открытый доступ.
- Успешная оплата связывается с пользователем и charge, повтор одного charge не создаёт второй grant.
- Фиксация оплаты и course_access атомарна; refund не снимает независимый ранее выданный ручной доступ и не закрывает доступ при наличии другой невозвращённой покупки.
- Возвраты ALREADY_REFUNDED и сбой БД после Telegram-вызова допускают повторную обработку.
- Оплата catchup-билета и его выдача атомарны; повтор после refund не восстанавливает неиспользованный билет.
- Административные выдачи требуют административной авторизации; ошибка grant откатывает approve.
- Новое LMS проверяет `aa_purchase_access` у связанных платных legacy-курсов; 28 текущих авторских курсов не имеют такой платной привязки.

## Проверки и артефакты

- Изолированный API-harness: 90/90, из них 86 штатных тестов и 4 сценария, которые **подтверждают наличие дефектов**, а не их исправление. Лог: `payments-api.log`.
- PGlite: обе основные проблемы воспроизведены на SQL-функциях из миграций. Повтор: `node test-results/full-audit/payments-repro.mjs`; лог `payments-pg.log`.
- `npm run test:audit-fixes` прошёл (лог `payments-atomic-regressions.log`).
- На рабочей Supabase не подтверждены применённые миграции, секреты, функция и порядок реальных webhook. Проверка реального Telegram/Stars и одновременных PostgreSQL-транзакций не проводилась. Отчёт — о проверенной версии кода и локально воспроизведённых состояниях.
