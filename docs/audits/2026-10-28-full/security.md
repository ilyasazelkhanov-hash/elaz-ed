# Аудит безопасности OG CRE8R

Проверен HEAD `cc14551`, 28 октября 2026. Только локальный аудит: настоящие Telegram/Supabase, секреты и пользовательские данные не затрагивались; продуктовый код не изменён.

## Подтверждённые проблемы

### SEC-01 · P2 · Публичный GET /setup меняет настройки бота

- Код: `supabase/functions/api/index.ts:2407`, реализация `:1325` (изменение settings.bot `:1330`, setWebhook `:1333`, меню `:1340`, команды `:1343`).
- Маршрутизация вызывает setup до member/admin-проверки и без ограничения метода. Анонимный GET возвращает200 и вызывает getMe, setWebhook, setChatMenuButton, setMyCommands, setMyShortDescription.
- Последствие: любой посетитель может принудительно повторять перенастройку бота и расходовать лимиты Telegram Bot API. Если параметры webhook/menu были изменены оператором вне этого setup, запрос перезаписывает их сохранёнными настройками проекта. Атакующий не выбирает произвольный URL и не получает токен; это не доказательство перехвата аккаунта.
- Исправление: POST с проверкой действующего администратора либо отдельного bootstrap-секрета; запрет GET для изменения состояния; ограничение частоты. Health оставить читающим.
- Доказательство: `security/repro.mjs`, `security/repro-results.json`; настоящая API-функция с подменёнными БД/Telegram, не сетевой запрос к рабочему боту.

### SEC-02 · P2 · При первой привязке канала не проверяется инициатор

- Код: `supabase/functions/api/index.ts:1294`, условие `:1297`, запись канала `:1298`.
- Если `settings.channel` отсутствует, любой реальный Telegram `my_chat_member` с переводом бота в администраторы канала становится основанием привязки. `mine.from.id` не сопоставляется с разрешёнными администраторами приложения.
- Сценарий: до владельца посторонний пользователь добавляет публичного бота в свой канал администратором. Telegram доставляет подлинный webhook; приложение начинает проверять подписку на посторонний канал.
- Последствие: неверный контроль доступа и блокировка аудитории при свежей установке или после сброса канала. Уже заданный канал условием защищён, текущий канал этим способом не перехватывается.
- Исправление: разрешать первичную привязку только заранее указанным Telegram ID/администраторам, либо явной командой подписанного администратора. Сохранять выбранный канал до начала автоматической обработки.
- Доказательство: `security/repro.mjs`, `security/repro-results.json`; инициатор777 не входит в settings.admins, но канал привязывается при пустом settings.channel. Подпись webhook в тесте синтетическая; предпосылка атаки — подлинное событие Telegram от канала атакующего, а не знание секрета webhook.

## Что проверено без найденного дефекта

- Все24 миграции применены к свежему PGlite/PostgreSQL: 81 public-таблица, RLS включён у каждой; ни у anon, ни у authenticated нет SELECT; все114 public-функций не имеют EXECUTE для этих ролей. Результат `security/rls-results.json`, воспроизведение `security/rls.mjs`.
- Роль администратора перепроверяется в member через атомарный resolve_admin; Academy actor берётся из подписанного пользователя, клиентские user_id/is_admin не заменяют его.
- Quiz API исключает рабочие ключи из публичного вопроса; проверка ответа/XP выполняется по сохранённой серверной попытке. Публичные материалы строятся по явному разрешённому списку полей.
- Приватные Academy-файлы: actor привязан к серверу; резервирование/скачивание через защищённый RPC, короткая подписанная ссылка; проверяются размер, тип, расширение и сигнатура. Публичное портфолио отделено от приватных вложений и требует согласия.
- ReactMarkdown не включает raw HTML; ссылки в Academy проходят safeAcademyUrl. Не найдено вызовов eval/new Function/dangerouslySetInnerHTML в основном интерфейсе. Это статическое наблюдение, а не исчерпывающий динамический XSS-фаззинг.
- `_shared/handler.ts` имеет собственную проверку Telegram/OIDC, CSRF cookie-сессии, проверку Origin, лимит тела запроса и rate-limit; это отдельный шлюз, а не доказательство наличия этих ограничений в обычном api/index.ts.

## Границы проверки

- Рабочие миграции/настройки/RLS могли отличаться от репозитория; live-доступ отсутствует, эта разница не проверена.
- В PGlite созданы заглушки схемы storage.buckets и extensions.gen_random_bytes для совместимости. Криптографическая случайность заглушки не оценивалась и не использовалась как доказательство безопасности; ни Storage-сервис, ни Edge-runtime не эмулируются полностью.
- Значения секретов не читались и не выводились. Поиск секретов в истории Git и полный secret scanner не запускались; проверены места использования server-only переменных и разделение frontend/server по коду.
- Аудит зависимостей, браузерная доступность, платежи/касса и эксплуатационная выкладка проверяются отдельными агентами. Полного пентеста, нагрузочного теста и проверки рабочего Telegram не было.
- Подтверждённых P0/P1 в проверенной области нет; это не гарантия их отсутствия во всём приложении.
