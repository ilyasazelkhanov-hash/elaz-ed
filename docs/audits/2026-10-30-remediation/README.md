## Выпуск — отдельное действие

Проверено локально: все 14 объявленных наборов test:* и четыре этапа production-сборки прошли, Academy — 200/200. После финальных правок отдельно повторены API (99/99), новые SQL/worker-регрессии (15/15), TypeScript и Vite build. Браузер — 10/10. Итог изолированного прогона и браузера сохранён в [validation.json](validation.json). CI workflow подготовлен; его удалённый результат следует смотреть в PR, локальный запуск не заменяет GitHub Actions.

1. Сохранить backup и убедиться, что существующие миграции, включая `20261029090000_academy_multiple_checks.sql`, применены. Затем применить по порядку новые миграции `20261030030610_atomic_progress_awards.sql`, `20261030030734_payment_purchase_intents.sql`, `20261030031554_admin_payment_search.sql`. Запустить Supabase database advisors и проверить ACL новых RPC/таблиц: только service_role, RLS у новых таблиц включён.
2. Настроить новый серверный `SETUP_SECRET`. Не использовать токен бота, не передавать секрет в URL или клиент. Для настройки бота применять только POST `/setup` с заголовком `x-setup-secret`. Проверить заранее сохранённые числовые Telegram ID администраторов; пустой канал теперь не привязывается по одному username.
3. Выпустить API вместе с модулем payments.ts. Сначала SQL, затем API: новая версия намеренно не откатывается молча к старой небезопасной логике. Существующие старые счета остаются совместимыми. На короткое время перекрытия старого/нового complete RPC PostgreSQL может выбрать одну транзакцию жертвой deadlock; повтор запроса безопасен.
4. Подготовить Vault `og_api_url` и существующий `settings.cron_key`, затем выполнить `scripts/payment-refunds-schedule.sql`. Проверить cron `og-payment-refunds`, HTTP-ответ worker и отсутствие необъяснённо растущего хвоста payment_refund_jobs. Ключ cron не публиковать; gateway Edge Function должен пропускать запрос к функции для её собственной проверки ключа, как существующий webhook. Подробности — [возвраты](../../payment-recovery.md).
5. Выпустить frontend после API. Проверить загрузку истории/поиск/повтор ошибки, доступность всех проверок урока и поведение клавиатуры. Реальный финансовый smoke-тест выполнять отдельно с согласованной тестовой покупкой; этот этап его не выполняет.

Не откатывать новые таблицы и не удалять задания возврата. При проблеме остановить новые покупки/выдачи на время исправления и сохранить новый worker для уже принятых заданий. Откат только frontend допустим после проверки контракта старого клиента; старый API не поддерживает новые purchase payload и транзакционные основания, поэтому его слепой откат небезопасен. Cron останавливается через `cron.unschedule('og-payment-refunds')`, но очередь сохраняется.

## Ограничения

Исторические ручные выдачи, нигде не сохранённые старым кодом, автоматически восстановить невозможно. Миграция использует существующие admin/invite-основания и одобренные заявки. Старые двойные списания автоматически массово не возвращаются: новый механизм обрабатывает вновь получаемые charge; исторический журнал требует отдельного разбора владельцем.

Локальные SQL-проверки используют PGlite, а API — синтетические Supabase/Telegram. Это не нагрузочный тест реального PostgreSQL и не проверка текущих прав рабочей Supabase. Браузерные проверки выполнены на локальном демо, без физического устройства и screen reader. Код workflow не доказывает, что required-check уже включён в настройках ветки GitHub.
