# Защитные пределы основного API

Исходная база аудита: `f9670b964a4bec8c288e37a32f7d6aeeaa8b48d8`. Перенесено на `13921dd` (main) с двумя изменениями после review: убрана общая квота до проверки входа и добавлен суточный льготный период для подтверждённой подписки при сбое Telegram (см. пункты 2 и 3). Изменения подготовлены и проверены только локально. Публикация, deployment, реальные платежи, вызовы Telegram/Supabase и изменение авторских материалов не выполнялись.

## Изменения

1. Основные POST-маршруты читают тело потоково с подсчётом байтов до `JSON.parse`. Превышение отменяет поток и возвращает `413 request_too_large`, даже без Content-Length или с заниженным заголовком. Некорректный JSON, массив, scalar/null и неверный UTF-8 возвращают `400 invalid_json`. Пустое тело по-прежнему означает `{}`. Клиентский `text/plain;charset=UTF-8` поддерживается.
2. Основные маршруты используют существующий PostgreSQL RPC `az_rate_limit`: квота после проверки подписи Telegram, до чтения/изменения пользовательских данных. Общей квоты до входа нет: её мог исчерпать один анонимный поток примерно в 50 запросов в секунду и тем самым закрыть приложение для всех. Запрос без верной подписи останавливается на HMAC-проверке и не обращается к БД. Только маршруты без входа через Telegram (`redeem`, `redeem_points`) получают собственную квоту на маршрут перед чтением тела; её исчерпание не затрагивает остальные маршруты. Ключ пользователя берётся только из подтверждённого Telegram ID. Forwarded/IP headers и client user_id на квоту не влияют. Ошибка или неизвестный ответ limiter возвращает `503 rate_limit_unavailable`, без продолжения операции. При превышении возвращается `429 rate_limited` и доступный через CORS `Retry-After: 60`.
3. Подписка перепроверяется после существующего пятиминутного TTL. Проверка подписки идёт почти на каждом запросе (`member()` и `boot()`), поэтому при сбое Telegram подтверждённые участники сохраняют доступ ещё до 24 часов с момента последнего подтверждения: сбой Telegram не должен выключать всё приложение. После 24 часов, а также при отсутствующем/некорректном/будущем timestamp сбой возвращает `503 membership_unavailable`, а не доступ или ложную отписку. Неподписанные пользователи при сбое остаются на экране подписки, как раньше. База при сбое не меняется. При forced refresh возраст подтверждения повторно проверяется после ожидания. Проверка getChatMember ограничена пятью секундами; неизвестный формат успешного ответа считается временной недоступностью.

## Пределы и совместимость

| Контур | Предел | Причина |
| --- | --- | --- |
| Обычный JSON, webhook, JSON advent_push | 512 KiB | Запас для существующих форм редактора; явный конечный предел вместо полного безусловного чтения |
| share_upload | 1.5 MiB | Сохраняет существующие 1 300 000 символов base64 плюс auth/envelope; проверка JPEG и размера image не меняется |
| academy | 12 MiB | Сохраняет существующий предел 4 000 000 UTF-16 символов payload, включая их обычное UTF-8 представление и envelope |
| academy_public | 2000 байт | Потоковый предел для коротких opaque code/slug; сохранён прежний 400 academy_invalid_payload |
| Маршруты без входа: redeem, redeem_points | 600 запросов / 60 сек на каждый маршрут | Защита БД от анонимного потока без общего порога для всего приложения; PIN кассира дополнительно защищён существующей блокировкой |
| Подтверждённый Telegram ID | 120 запросов / 60 сек суммарно по маршрутам | Запас для обычной навигации/квиза; повторный вход и смена маршрута не создают новую квоту |
| health/api | 120 запросов / 60 сек отдельно | Публичная диагностика не расходует квоту приложения |

Пределы частоты являются стартовыми защитными значениями, а не результатом измерения реального трафика. Их следует сопоставить с законными пиками перед выпуском. Бинарные файлы Academy идут прямо в Storage и не проходят через этот JSON reader. Чрезмерное пробельное/escape-раздувание JSON теперь может быть отклонено, даже если после parse payload был бы меньше.

Webhook проверяет секрет до чтения ограниченного JSON. Webhook, setup и cron не используют общую пользовательскую квоту: массовые запросы к приложению не должны блокировать подтверждения оплаты и фоновые операции. Их действующие секреты остаются обязательными. Пустой cron JSON поддерживается; синтаксически неверный JSON больше не запускает advent_push с настройками по умолчанию. Маршруты, не читающие тело, не буферизуют его. OPTIONS и неизвестные маршруты не вызывают limiter.

## Зависимость перед выпуском

Новая миграция не требуется: `az_rate_limit` и `az_rate_limits` уже определены в `20261016195015_az_master.sql` и используются существующим academy_public. Теперь основной API и health также зависят от этого RPC. Перед отдельным разрешённым выпуском необходимо проверить наличие RPC, таблицы и service-role прав в целевой БД; отсутствие зависимости намеренно даёт 503, а не отключает защиту. Реально развёрнутая схема в этой работе не проверялась.

## Ограничения

- Это защита на уровне приложения, не полноценная DDoS-защита. Квоту анонимного маршрута может исчерпать злоумышленник; это временно ограничит только этот маршрут (кассу). Анонимные запросы к остальным маршрутам не ограничены по частоте, но и не доходят до БД. Каждый вызов limiter обращается к БД; нужны отдельные инфраструктурные ограничения и наблюдение за 429/503.
- Поток ограничен по объёму, но не по времени получения. Slow-body завершится по инфраструктурному таймауту. Один уже выданный runtime большой chunk существует до его проверки.
- Для совместимости academy оставлен более крупный 12 MiB предел до проверки подписанного пользователя. Дополнительное разделение import/обычных действий потребовало бы изменения контракта.
- Свежий положительный cache может сохранять доступ до пяти минут после ухода из канала, если webhook не доставлен. Во время сбоя Telegram ушедший из канала может сохранять доступ до 24 часов с последнего подтверждения. Доступ даёт бесплатная подписка на канал, а не оплата, поэтому доступность приложения важнее. Если сбой длится дольше 24 часов, такие пользователи временно получат 503.
- Не выполнялись полная frontend сборка, test:all, Deno typecheck/runtime, browser UI проверка, реальная PostgreSQL нагрузка или проверка deployed-конфигурации. Node 24 mock/PGlite проверки не заменяют эти этапы.
- Настоящие секреты, запросы к production, реальные сообщения/платежи и платные учебные тексты не использовались.
