# News publishing

Every three days, the Codex automation researches and publishes a batch of distinct actual news articles: aim for **3–5 verified announcements**, and include more when they are valuable. Publish fewer or skip the run when suitable verified announcements are unavailable. Open current primary sources, confirm announcement dates and factual claims, and write original Russian summaries with concrete implications and limitations. Choose a relevant public cover image for every article, preferably its official announcement hero image. Never invent events, reuse course lessons, republish an existing article, or manufacture posts to meet a quota.

The CLI validates structure, dates, duplication, text overlap and cover image accessibility/identity. It cannot establish that a source is primary, that an announcement happened, that an image depicts that announcement, or that claims are true; the researching automation must do those checks. The CLI fetches image bytes but does not fact-check article pages or generate content.

## Run

Use Node 24 and the authenticated installed Supabase executable. Set `SUPABASE_CLI` to its absolute executable path and explicitly set `RELEASE_PROJECT_REF=dcdepwdxvadhludnubis`. Run from this checkout:

```powershell
node scripts/publish-news.mjs --file test-results/news-draft.json --dry-run
node scripts/publish-news.mjs --file test-results/news-draft.json --publish
```

Omitting the mode defaults to dry run. Dry run performs a targeted read and validation with **no database writes**. Keep the draft identical between review and publication. The JSON file accepts one article object for compatibility or an array of **1–20 article objects**. `--publish` inserts the new articles together as published standalone `lesson` rows, with `course_id=null`, `news_eligible=true`, and editorial metadata. It does not edit existing lessons, deploy APIs, apply migrations, or send Telegram messages. It requires the news/editorial schema migration to be present.

The JSON object contains `title` (8–240 characters), `subtitle` (8–500), `body` (at least 80 words, at most 50,000 characters), `category` (2–80), `minutes` (integer 1–30), `event_on` (`YYYY-MM-DD`), and a required public HTTPS `cover_url`. Optional presentation fields are `emoji` and `gradient`. Include the ISO event date and at least one complete primary source URL visibly in `body`, so readers using older APIs can see provenance.

`editorial` must contain `kind: "update"`, `checked_on`, `review_due`, `reviewer`, and `sources: [{"title": "Official announcement", "url": "https://official.example/blog/announcement"}]`. Event dates must be within the preceding seven calendar days, never future dates. The check must have happened today or yesterday, after the event date; the next review must not be overdue. Dates use `Asia/Qyzylorda`. URL shape validation does not prove source authority.

## Guards and outcomes

- Every article must validate and pass the course guard before any insertion. Duplicate articles within the requested batch reject the whole batch. An invalid or course-derived entry cannot result in partial publication.
- Every distinct cover URL is checked during both dry run and publish before database writes. The checker uses GET with a byte range, a 10-second deadline, at most three redirects, and a 2 MiB maximum body. It requires at least 256 bytes, JPEG/PNG/WebP MIME and matching file signatures/container boundaries; HTML, SVG, inaccessible URLs and truncated or oversized data fail closed. Use direct public image files rather than a page URL. These checks identify the file format and accessibility, not its editorial relevance or rights.
- Covers require HTTPS without credentials or nonstandard ports. Localhost, private/reserved literal IPs, internal DNS answers and unsafe redirect destinations are rejected. The native transport pins each request to the DNS addresses it validated, preserving the original HTTPS hostname for certificate verification. Failed image checks publish no articles. Existing articles returned as duplicates are not edited to add or replace a cover; use a separately reviewed targeted update for that.
- Exact normalized title or body matches identify existing articles. Canonical source URL matches also identify the same dated event. URL tracking parameters and fragments do not create a new source identity. The CLI persists `editorial.event_on` so later announcements on the same rolling changelog can be published as distinct dated news. Prefer dedicated announcement posts when available. Legacy rolling changelog/release-notes rows without a saved event date do not permanently reserve that URL.
- Existing articles are skipped; all remaining articles are inserted together. If every article already exists, `duplicate` returns the original IDs without writing. Results include ordered `ids`; single-article calls also retain `id` and `content_key`. `inserted_ids` identifies the new rows.
- The CLI checks published course-bound bodies and both required authored corpora: `content/ai-practice-2026-10-25/training.json` (14 historical lessons) and `content/ai-practice-2026-10-25/paths.json` (33 current lessons). Missing or malformed local corpora stop the run. An exact course body, a candidate of at least 40 words wholly copied as a contiguous excerpt, or at least 60% candidate containment with 100 shared unique five-word shingles is rejected. Shared topical vocabulary alone is allowed. Course bodies are loaded only by Node, never bundled into frontend code or printed.
- `dry_run` means validation passed; `publish_count` shows how many new articles would be inserted. `not_due` means fewer than three local calendar days have elapsed since the last automatic **batch**, including when a requested batch contains some existing articles. The cadence is checked once for the complete batch. A calendar check is not the recurring scheduler: Codex supplies the three-day schedule.
- Publishing takes an advisory transaction lock and a lessons table lock, rechecks the source catalog signature and cadence, and atomically inserts all new lessons, per-article `news-automation:receipt:<SHA256-content-key>` records, one `news-automation:batch-receipt:<batch-key>`, and `news-automation:last`. The batch key hashes the ordered article content keys. The last state records the batch key and ordered lesson IDs only after all insertions succeed. Any failure rolls back the complete batch and its receipts. Other settings remain intact.
- `catalog_changed` requires another dry run against the current catalog. An uncertain CLI/network result requires checking the batch receipt before retrying; a retry of the identical ordered batch is idempotent and returns the same IDs. Never change the articles merely to get around duplicate or cadence guards.

Only IDs, counts, dates, percentages and hashes appear in result/guard reports. Targeted catalog rows and subprocess output remain internal. Temporary SQL lives under ignored `test-results/news-publisher/`, with private file permissions where supported, and is removed after the call. Do not print drafts, course catalogs, raw SQL, CLI stderr, access tokens or private database snapshots into automation output.

Verify locally with `node --experimental-strip-types --test tests/news-policy.test.mjs tests/news-publish.test.mjs`.
