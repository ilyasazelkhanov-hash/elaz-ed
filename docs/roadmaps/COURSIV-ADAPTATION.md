Версия плана: 1.0. Дата: 2026-11-12. Проверенный исходный снимок: `cd09c91a9709f8988cf825077a4afd9d1c61d523`.

Это план реализации с проверяемыми критериями, а не перечень обещаний. Исследование: «Coursiv и развитие OG CRE8R», 17 страниц, переданные владельцу DOCX/PDF. Платная сессия Coursiv не тестировалась. Официальные промоскриншоты не доказывают фактическую реализацию всех функций. Оценки, жалобы и маркетинговые заявления не являются доказательством учебной эффективности.

## Правила ведения

- `source-present`: функция найдена в исходниках, это не подтверждение развёрнутого backend или результата в реальном аккаунте.
- `partial`: часть сценария существует; указан конкретный пробел.
- `in-progress`: работа назначена, но ещё не принята и не опубликована.
- `planned`: критерии определены, работа не начата в этом плане.
- `deployment-check`: нужен отдельный разрешённый smoke или проверка миграций/сервера.
- `deferred`: отдельный эксперимент или инфраструктурное решение, не текущий выпуск.
- `verified-live` разрешён только с commit, датой, средой, шагами проверки и оговорками. Ни один новый пункт этого документа пока не имеет этого статуса.

При каждом выпуске обновлять конкретные строки, не переписывать исходный baseline. Хранить ссылку на тест и проверку реального сценария. Новая версия UI не означает автоматический выпуск миграций, контента или прав доступа. План не даёт разрешения удалять данные, покупать сервисы, расширять полномочия, публиковать работы учащихся или отправлять им сообщения.

## Последовательность без параллельных систем

1. Сохранить этот baseline, вести C01 и C07 отдельными workstream с общей проверкой UX. Не объявлять работу завершённой до тестов и интеграции.
2. Проверить существующие C04/C05/C18. Наличие server code не доказывает миграции. Не тратить деньги и не удалять записи в smoke.
3. Принять один вертикальный сценарий: выбрать цель -> увидеть следующий доступный шаг -> выполнить практику -> сохранить/экспортировать -> понять статус результата -> продолжить.
4. Подключить существующие placement/rubric/portfolio, если они реально доступны. При недоступном сервере явно показать локальную практику и её пределы, не скрыто подменять backend.
5. Расширять авторскую переработку по курсам после пилота; перечислять обновлённые коды и проверенные критерии, не писать «все курсы улучшены».
6. Затем запускать измерение переноса навыка, повторение и новые среды. Не копировать подписной funnel Coursiv ради конверсии без прозрачных условий.

## Текущий срез, согласованный между исполнителями

Это назначенный scope, не отметка завершения:

- `learning_path`: LearningNext на главной, после Dots/daily/advent в сохранённом порядке пользователя; объяснение следующего действия; scoped preference/последний бесплатный шаг; платное продолжение только по серверным completion/access. Возможная короткая самопроверка опытного не является официальной аттестацией или снятием lock. Планируемые области: Home, LearningNext, learning-next, FreeStart и OGPractice.
- `practice_learning`: FreeStart/PracticeReader, локальный артефакт, критерии из существующих guides, явное сохранение/экспорт. Нет независимой оценки, серверной синхронизации, начисления XP или сертификата. Это срез C07, не завершение C03/C11/C12.
- `research_plan_og`: только этот документ. Runtime, API, БД, роли и CI не меняются.

После интеграции уточнить характер хранилища предпочтений: baseline использует sessionStorage, новый срез может использовать scoped localStorage. Ни тот, ни другой вариант не должен называться cross-device синхронизацией. Показать пользователю реальное ограничение хранения работы.

## Критические границы доступа

- Обычные изменения кода и UI относятся к поручению владельца; публикация производится координирующим исполнителем после проверки exact SHA и применимого подтверждения.
- Миграции меняющие продакшен и доступ к данным требуют отдельной оценки совместимости, backup и rollback. Не удалять данные в рамках этой дорожной карты.
- Постоянный перенос черновиков на сервер меняет хранение пользовательского ввода. Нужны минимизация данных, RLS, срок хранения и видимое объяснение, особенно для медицинских примеров.
- Платный LLM, новая подписка, карты/платежи, расширение прав сервиса и добавление новых внешних получателей не следуют автоматически из «внедрить исследование».
- Публикация работ учащихся только по их отдельному согласию. Зачёт/сертификат только по существующим проверенным правилам, а не за нажатие CTA.

## Чек-лист приёмки каждого среза

- [ ] Указаны commit, baseline, изменённые файлы и IDs плана.
- [ ] Нет обхода access/enrollment/assessment на клиенте.
- [ ] Проверены guest/new/continuing/completed/inaccessible/error/timeout и смена пользователя.
- [ ] Черновик, работа и зачёт имеют честно разные состояния.
- [ ] Фокус, возврат, повторное нажатие, длинный текст, 320/390 и reduced motion проверены с оговорками.
- [ ] Unit/integration и итоговый `npm run test:all` пройдены на exact integration SHA. Записаны не запущенные тесты.
- [ ] GitHub SHA, CI, Vercel и backend/migrations имеют отдельные статусы.
- [ ] Проверен реальный аккаунт или прямо указано, что был только demo.
- [ ] Документ/контент/БД изменения перечислены отдельно, rollback не уничтожает данные.

## Измерение пилота

Минимальные показатели: время до первого сохранённого результата; доля работ с выполненной рубрикой; выполнение нового аналогичного задания без подсказки; восстановление незавершённой работы; неопределённые оплаты/повторы; трудности на телефоне и с клавиатуры. Для каждого сохранять знаменатель, окно времени и тип аудитории. Не использовать общий XP как метрику обучения. До определения privacy-safe схемы и baseline это план измерения, не существующий dashboard.
