## VC-201-M4-L1 · Выбор уровня проверки

В этом проекте интеграционные тесты запускают реальный HTTP-сервер на свободном порту и делают запросы к SQLite. Они проверяют связь маршрута, сессии и данных. Отдельный тест арифметики не обнаружит пропущенное условие владельца, а браузерная проверка одного аккаунта может не заметить утечку другому. Выбирай уровень по конкретному риску.

Браузерный сценарий должен пройти регистрацию, ввод времени и появление записи в списке. Серверный сценарий отдельно проверяет чтение чужого ID. Проверка после перезапуска доказывает сохранение в файле и одновременно ожидаемую потерю сессии в памяти. Эти результаты нельзя объединять в расплывчатое «всё работает».

Smoke после локального запуска — короткая проверка страницы и одного сохранения. Она помогает быстро заметить поломку, но не заменяет набор негативных случаев. Составь карту: риск, подходящий тест, ожидаемый результат, что тест не покрывает. Перед расширением набора проверь, способен ли каждый тест упасть при соответствующей ошибке. Зелёная проверка, которая не вызывает нужный маршрут или не проверяет ответ, не даёт полезного свидетельства готовности.

## VC-201-M4-L2 · Миграции и выпуск

CREATE TABLE IF NOT EXISTS в стартере создаёт исходную схему при первом запуске. Это повторяемая инициализация, но не универсальный механизм миграций. Если добавить новое обязательное поле, команда не изменит уже существующую таблицу. Для развития проекта нужны версия схемы, отдельное преобразование и проверка перехода на копии прежних данных.

Разбери добавление необязательной заметки к записи. Сначала опиши, как старый клиент работает с новым сервером и как обрабатываются существующие строки без заметки. Затем подготовь миграцию в отдельной тестовой копии базы. Проверь старую запись и создание новой. Не удаляй файл базы как способ «успешно применить» изменение: это уничтожает проверяемый переход.

Для CI подходит команда node --test server.test.mjs на Node 24. База тестов создаётся во временной папке, а порт выбирается системой. Выпуск рабочего сервиса дополнительно требует резервного копирования и плана совместимого отката. В упражнении подготовь порядок действий и тест перехода; не запускай миграцию на реальных данных. Отдельно запиши, почему откат исходников не всегда автоматически возвращает прежнюю схему базы.

## VC-201-M4-L3 · Диагностика по воспроизводимому запросу

Начни с точного наблюдения: маршрут, код ответа, форма входа и действие пользователя. Не копируй токен сессии в общий отчёт. Для занятого времени 409 — ожидаемое поведение, а для необработанной ошибки SQL 500 требуется диагностика. Успешный HTTP-ответ ещё не доказывает появление строки: перечитай список после сохранения.

В отдельной папке запусти сервер с путём BOOKING_DB внутри отсутствующего каталога. Ошибка открытия базы должна возникнуть при старте, до готовности порта. Исправь путь, затем проверь запуск и сохранение. Это проблема среды, а не причина переписывать SQL бронирования.

Для ошибки клиента проверь вкладку сети и сопоставь фактическое поле requestKey с контрактом сервера. Если ответ потерян, повторяй то же действие с прежним ключом. Смена ключа превращает повтор в новую операцию и может дать конфликт занятого слота. Запиши две гипотезы и различающую проверку для каждой. После исправления повтори исходный сценарий и связанные тесты, а не только удобный положительный пример с другим временем.

## VC-201-M4-L4 · Приёмка полного учебного MVP

Защити проект через пользовательский сценарий и прямые API-проверки. Создай два вымышленных аккаунта, запиши первого на свободный слот и покажи, что второй не видит его данные. Перезапусти сервер с тем же файлом базы: записи должны сохраниться, а вход нужно выполнить заново. Объясни, почему это ожидаемо при сессиях в памяти.

Покажи повтор одного запроса с тем же ключом и конфликт при попытке другого аккаунта занять время. Затем открой код транзакции и объясни связь bookings и outbox. Скажи прямо: черновик уведомления сохранён, но доставка не реализована. Такая точность важнее впечатления, будто у стенда уже есть рабочая почта.

В сдачу входят исходники, инструкция Node 24, схема, контракты, тестовый отчёт и ограничения. Продемонстрируй одну свою доработку, например отмену с проверкой владельца, и объясни её крайние случаи. Для коммерческого выпуска отдельно нужны эксплуатационные решения: HTTPS, ограничение запросов, управление сессиями, резервное копирование и процесс миграций. Локальный зачёт подтверждает понимание полного пути данных и проверки прав, а не готовность принимать реальные записи клиентов.
