## VC-201-M1-L1 · Сценарий до архитектуры

Пользователь хочет занять свободное время и позднее увидеть свою запись. Это сценарий, а не список технологий. Раздели его на действия: создать учебный аккаунт, войти, выбрать слот, сохранить запись, повторно открыть список. Для каждого действия запиши вход, результат и возможный отказ. Из формулировки «записаться на ремонт» ещё не следует наличие оплаты, уведомлений и административной панели.

В проекте доступны учебные часы января 2030 года. Это намеренное ограничение стенда, а не календарь настоящей мастерской. При успешном запросе запись сохраняется в SQLite, а текст интерфейса прямо говорит, что уведомление не отправлено. Для занятого времени пользователь получает понятный отказ. Другой клиент не должен увидеть чужую запись даже по прямому адресу.

Напиши три истории: успешная запись, повтор после потерянного ответа, попытка чтения чужого ID. Последняя история задаёт важное требование безопасности, которое не видно на макете. В каждом случае определи проверяемый исход до изменения кода.

## VC-201-M1-L2 · Контракт API и смысл таблиц

API — договор между интерфейсом и сервером. В проекте POST /register создаёт аккаунт, POST /login возвращает сессию, GET /bookings показывает собственные записи. POST /bookings принимает slot и requestKey. Поле user_id клиент не выбирает: сервер получает владельца из проверенной сессии. Это часть контракта доступа, а не рекомендация интерфейсу.

SQLite хранит пользователей и записи. Первичный ключ отличает строки, внешний ключ связывает запись с пользователем, уникальный slot запрещает двойную бронь. SQL-запрос использует параметры вместо сборки строки из пользовательского ввода. Иначе данные вроде кавычки могли бы изменить смысл запроса.

Сравни HTTP 400, 401, 404 и 409: неверные данные, отсутствие входа, недоступная запись и конфликт состояния требуют разных действий пользователя. Код 200 с текстом ошибки внутри не равен успешной записи. Составь таблицу маршрутов, входов, ответов и проверок владельца. Отдельно отметь, какие значения назначает сервер, чтобы случайно не доверить клиенту права при следующей доработке.

## VC-201-M1-L3 · Модель данных и ограничения

Нарисуй связь users 1 → N bookings и bookings 1 → 1 outbox. Аккаунт может иметь несколько записей, но каждая запись принадлежит ровно одному аккаунту. Outbox хранит черновик будущего уведомления; это ещё не доставка сообщения. Уникальность booking_id предотвращает несколько черновиков одного события.

У bookings есть два разных ограничения. Уникальный slot не позволяет двум клиентам занять одно время. Пара user_id и request_key позволяет узнать повтор того же запроса. Эти условия решают разные задачи: ключ повтора не заменяет защиту слота от другого пользователя.

Рассмотри два последовательных запроса на одно время от разных аккаунтов. Предварительное чтение «время свободно» не гарантирует последующую запись: состояние могло измениться. Окончательную защиту обеспечивает ограничение базы в момент INSERT. Сервер преобразует такой конфликт в 409. Подготовь схему и два примера конфликтующих вставок. Для каждого назови ограничение, которое должно сработать. Не добавляй удаление пользователя без решения о судьбе его записей и связанных уведомлений.

## VC-201-M1-L4 · Два варианта архитектуры

Первый вариант хранит записи только в localStorage браузера. Он подходит для демонстрации интерфейса одному человеку, но другой браузер не узнает о занятом времени. Второй вариант использует общий сервер и базу. Он позволяет проверять занятость и владельца централизованно, зато требует эксплуатации и защиты доступа. Выбор зависит от обещания продукта.

Наш проект использует Node и SQLite на одной машине. Такой стенд помогает изучить полный путь запроса без отдельной службы базы данных. Это не обещание горизонтального масштабирования: несколько независимых файлов SQLite на разных серверах не станут одной общей базой. Сессии хранятся в памяти и после перезапуска исчезают, тогда как записи остаются на диске.

Оформи короткое архитектурное решение: задача, два варианта, выбранный подход, последствия. Укажи, почему для учебного прототипа достаточно одного процесса и чего не хватает для реального сервиса: HTTPS, ограничения частоты входа, резервного копирования, управления жизненным циклом данных. Разделение ограничений помогает не выдавать рабочее локальное демо за готовый коммерческий продукт.
