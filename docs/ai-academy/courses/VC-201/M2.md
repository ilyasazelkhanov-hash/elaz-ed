## VC-201-M2-L1 · Контекст агента для серверной задачи

Чтобы изменить поведение бронирования, агенту нужны контракт API, схема базы, обработчик и соответствующие тесты. Передача всей переписки о дизайне не заменяет этих файлов. Попроси сначала объяснить, где вычисляется владелец и какой запрос ограничивает чтение записей. Если ответ не ссылается на условие user_id в SQL, контекст или понимание неполны.

Дай узкую задачу: добавить проверку недопустимой минуты слота, не меняя правило владельца. Ожидаемый отказ для 09:30 уже определён форматом учебного стенда. До правки агент должен назвать проверку и файл. После правки он показывает diff и фактический результат теста.

Когда разговор становится длинным, сохрани короткую актуальную спецификацию с принятыми решениями. Устаревшее сообщение о разрешении любого времени не должно незаметно заменить текущий контракт. Не прикладывай к запросу реальные пароли или файл рабочей базы. Учебные аккаунты создаются на синтетических данных; для диагностики достаточно формы запроса и кода ответа без значения токена.

### Практика

Открой отдельную учебную копию проекта. Результат занятия: Карта контекста одной серверной задачи. До изменения запиши исходное поведение, затем выполни описанный сценарий и сохрани фактический результат. Для неудачного запуска укажи конкретную гипотезу и следующую проверку. Не изменяй ожидание теста ради совпадения с ошибкой.

### Самопроверка

- Найдены обработчик и проверка владельца
- Пример недопустимого времени задан заранее
- Токены и реальные данные исключены

### Подсказка

Если задача кажется большой, сократи её до одного запроса и одного ожидаемого ответа. Проследи путь: интерфейс → HTTP → проверка сессии → SQL → ответ. Попроси AI объяснить только непонятный переход и сравни объяснение с кодом.

Уточни, что client.mjs и server.mjs используют один контракт, а схема хранится в начале сервера.

Перед началом прочитай git status. Для выбранной задачи создай ветку в своём учебном репозитории, если работаешь с Git. Ветка хранит линию истории, но не запускает отдельную базу: файл booking.sqlite остаётся обычным файлом рабочей папки. Для независимого эксперимента используй другой BOOKING_DB, а не рассчитывай на изоляцию данных по имени ветки.

Добавь локальный файл базы и журналы в .gitignore учебной копии до первого коммита. Это не удаляет уже закоммиченные данные из истории, поэтому сначала проверь состав файлов. ## VC-201-M2-L3 · Маленькие законченные изменения

Инкремент должен проходить полный путь от требования до наблюдаемого результата. Для кнопки обновления списка недостаточно нарисовать элемент: нужно связать действие с GET /bookings, обработать ошибку входа и показать только записи текущего владельца. Такой небольшой кусок можно проверить целиком до следующей функции.

Раздели добавление отмены записи на шаги: сначала контракт и правило владельца, затем серверный тест, затем обработчик, затем интерфейс и проверка повторного нажатия. Не начинай с массового удаления строк и изменения всех экранов. Реши заранее, что происходит с уведомлением и можно ли повторить отмену безопасно. В исходном проекте отмена намеренно отсутствует.

Выполни только первый инкремент — спецификацию и тест ожидаемого отказа для чужого владельца в своей копии. Красный тест здесь показывает отсутствие новой функции; его нельзя выдавать за готовый релиз. После реализации повторяют существующие проверки записи, конфликтов и сохранения после перезапуска. Составь план так, чтобы каждый следующий шаг опирался на результат предыдущего и не требовал скрытого ручного изменения базы.

## VC-201-M2-L4 · Ревью опасных правок

В корректном чтении одной записи используются одновременно id и user_id. Правка, которая оставляет только id, может не сломать демонстрацию одного аккаунта, но открывает чужие данные. Для ревью важен смысл условия, а не размер diff. Одна удалённая проверка бывает опаснее большого изменения оформления.

Во временной копии убери ограничение владельца только из запроса отдельной записи и запусти server.test.mjs. Проверка чтения чужого ID должна обнаружить дефект. После эксперимента восстанови исходный запрос. Сохрани объяснение, почему скрытие ссылки в интерфейсе не устраняет проблему прямого API-запроса.

Проверь также регистрацию: пароль преобразуется через scrypt с отдельной солью, а наружу возвращается только токен сессии. Если агент предлагает отправлять пользователю всю строку users для удобства отладки, это расширяет утечку данных. Для отчёта достаточно кода ошибки и обезличенного сценария. Составь список мест доверия: ввод браузера, заголовок авторизации, серверная сессия и база. На каждом переходе отметь, что уже проверено и чему доверять ещё нельзя.
