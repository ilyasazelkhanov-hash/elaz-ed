## Урок 1 из 16 · 1.1 · Grain, SELECT и агрегаты

Код занятия: `DT-201-M1-L1`.

Это первый урок курса. Дальше двигайся по порядку.

[Следующий урок →: Урок 2 · 1.2 · Напиши SQL и проверь независимо](M1.md#lesson-dt-201-m1-l2)

Grain — то, что означает одна строка. В orders это уникальный принятый заказ, в order_items — строка услуги. SELECT выбирает поля, JOIN связывает уровни, GROUP BY собирает группы. Ошибки возникают, когда сумма верхнего уровня повторяется на каждой дочерней строке.

Для общей выручки достаточно `SELECT sum(total_kzt) FROM orders`: результат 13500. После JOIN с order_items та же header-сумма становится 20000, потому что некоторые заказы имеют несколько услуг. SQL выполнен успешно, но выбран неправильный уровень расчёта.

Нарисуй обе таблицы и связь 1:N, затем подпиши единицу каждой суммы. Не пытайся исправить результат произвольным DISTINCT по сумме: разные заказы могут иметь одинаковую цену. Сдай два запроса, ручной расчёт и объяснение, почему уникальность нужна по ключу заказа. Вопрос к AI должен включать grain и ожидаемый результат на маленьком примере, а не только просьбу «посчитать выручку».

### Практика

Результат: Схема grain и два разных результата. До запроса укажи grain, единицу и ожидаемую проверку. После исполнения сверяй промежуточные строки и итог отдельно. Сохрани исходный CSV и правила исключения, чтобы вывод можно было повторить.

### Самопроверка

- Единица строки названа
- Успешный SQL не принят как верная метрика
- DISTINCT по цене не подменяет ключ

### Подсказка

Если сумма неверна, сначала посмотри строки до GROUP BY. Если вывод слишком сильный, проверь дизайн сравнения и недостающие факторы.

[Скачать аналитическую лабораторию](https://github.com/ilyasazelkhanov-hash/elaz-ed/raw/refs/heads/main/public/learning/academy/data-lab.zip). На Python 3.12 выполни `python3 -m unittest test_analysis.py`; SQL проверяется через `python3 query.py "SELECT sum(total_kzt) AS revenue FROM orders"`. HTML-отчёт открывай через локальный HTTP-сервер на порту 5193.

### Результат занятия

Схема grain и два разных результата

### Критерии

- Единица строки названа
- Успешный SQL не принят как верная метрика

Добавь группировку по channel и сравни суммы 6200, 4300 и 3000. Итог по группам должен совпасть с общей суммой. Совпадение необходимо, но ещё не доказывает правильность исходных правил очистки.

Попроси AI объяснить запрос и потенциальный риск, затем проверь код сам. Не выполняй предложенный DROP или ATTACH ради удобства анализа. Учебный authorizer допускает только чтение двух таблиц и ограниченный набор функций, а CLI возвращает отказ для других действий. Сдай запрос, результат и независимую ручную сверку одного канала. Отдельно перечисли предположения о валюте, уникальности и периоде, которые SQL не может вывести из названия поля автоматически.

## Урок 4 из 16 · 1.4 · Неверная кратность JOIN

Код занятия: `DT-201-M1-L4`.

[← Предыдущий урок: Урок 3 · 1.3 · Три KPI с явным знаменателем](M1.md#lesson-dt-201-m1-l3)

[Следующий урок →: Урок 5 · 2.1 · Пропуски, дубли и дрейф типов](M2.md#lesson-dt-201-m2-l1)

Возьми O001: header 1000, услуги 600 и 400. JOIN даёт две строки, и суммирование o.total_kzt посчитает 1000 дважды. Для O004 и O006 возникает та же проблема, поэтому общий результат завышается до 20000.

Решение зависит от вопроса. Если нужна общая header-выручка, агрегируй orders без JOIN. Если требуется сумма строк, используй amount_kzt. Если фильтр находится в дочерней таблице, сначала определи нужные order_id и сохрани один вклад каждого заказа.

Построй маленькую промежуточную выдачу с order_id и обоими денежными полями. Это помогает увидеть размножение до агрегирования. Не «чините» число вычитанием разницы или DISTINCT по total_kzt: одинаковая сумма у разных заказов допустима. Сдай ошибочный и корректный запросы, объяснение по одному заказу и тест, который заметит возвращение дефекта. Укажи, какая бизнес-семантика выбрана, а не только что изменён синтаксис SQL.

### Практика

- Есть регрессия по заказу с двумя услугами
