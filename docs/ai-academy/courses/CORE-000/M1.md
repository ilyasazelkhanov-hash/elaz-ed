## Урок 1 из 16 · 1.1 · Основные типы моделей и ограничения

Код занятия: `CORE-000-M1-L1`.

Это первый урок курса. Дальше двигайся по порядку.

[Следующий урок →: Урок 2 · 1.2 · От простого промпта к хорошему ТЗ](M1.md#lesson-core-000-m1-l2)

Языковая модель генерирует продолжение текста на основе входа и изученных закономерностей. Это полезно для черновиков, преобразования текста, извлечения полей и объяснений. Связность ответа сама по себе не доказывает истинность. Мультимодальная модель принимает несколько видов входа, например изображение и текст, однако доступные режимы зависят от конкретного продукта. Модель эмбеддингов превращает материал в числовое представление для поиска похожих фрагментов; такой поиск не равен проверке фактов. Генератор изображений создаёт визуальные варианты, а распознавание речи помогает получить текст записи.

Разделяйте модель и приложение. Поиск в интернете, чтение файлов, калькулятор и отправка письма могут быть отдельными инструментами приложения. Если поиск не был запущен, нельзя считать ответ проверенным по свежим страницам. Если приложение не открыло аудио, нельзя принимать заявление «я прослушал запись».

Для мастерской «Маяк» подходят черновик FAQ по утверждённым правилам и классификация обращений. Обещание точного срока ремонта требует актуальной системы заказов. Решение о возврате денег требует полномочий и проверки человеком. Ошибки здесь имеют разную цену: неудачный заголовок исправляется быстро, неверное обязательство перед клиентом становится проблемой обслуживания.

**Практика.** Возьмите четыре задачи: придумать заголовки; извлечь номера заказов; назвать сегодняшнюю загрузку мастеров; автоматически одобрить возврат. Для каждой укажите подходящий класс решения, необходимые входные данные, способ проверки и ответственного. Отметьте, где генерация вообще не нужна. Ожидаемый результат — четыре обоснованных маршрута, включая запрос к источнику для загрузки и человеческое решение по возврату. Не называйте одну модель универсальным победителем.

Дополнительно придумайте отказоустойчивое поведение: если номер заказа не найден, система должна запросить уточнение, а не создавать правдоподобный номер. Такой резервный путь часто важнее красивого текста.

### Результат занятия

Карта применимости для четырёх задач мастерской

### Критерии

- Различены модель, приложение и инструмент
- Для каждой задачи указан проверяемый источник входных данных
- Есть сценарий неопределённости и ответственный человек

## Урок 2 из 16 · 1.2 · От простого промпта к хорошему ТЗ

Код занятия: `CORE-000-M1-L2`.

[← Предыдущий урок: Урок 1 · 1.1 · Основные типы моделей и ограничения](M1.md#lesson-core-000-m1-l1)

[Следующий урок →: Урок 3 · 1.3 · Эксперимент: одна задача в двух моделях](M1.md#lesson-core-000-m1-l3)

Запрос «сделай хороший FAQ» оставляет модели выбирать аудиторию, факты и формат. Для клиентского результата сначала определите, кто будет читать материал и какое действие он должен поддержать. Затем отделите достоверные исходные сведения от пожеланий к стилю. Ограничение «не придумывай» полезно как инструкция, но не заменяет проверку результата.

Хорошее ТЗ содержит цель, доступные данные, границы задачи, формат ответа и критерии приёмки. Для «Маяка» исходные сведения таковы: диагностика проводится после приёма устройства; стоимость согласуется после диагностики; сроки сообщаются индивидуально. Это синтетический учебный регламент, а не сведения о существующей компании. Недостающие условия гарантии должны остаться вопросом к владельцу.

Рабочий запрос можно сформулировать так: «Подготовь четыре пары вопрос–ответ для клиента мастерской по тексту регламента ниже. Используй только указанные факты. Если данных нет, напиши “требует уточнения”. Каждый ответ — до двух предложений. После FAQ выведи список вопросов владельцу. Не обещай цену или срок». Входной регламент разместите отдельным блоком с меткой “данные”.

**Практика.** Сначала сохраните ответ на исходный короткий запрос. Затем составьте ТЗ и получите второй ответ. Сравните их по трём признакам: неподтверждённые обещания, покрытие правил, пригодность формата. Подсчитайте нарушения, а не ограничивайтесь впечатлением «стало лучше». Ожидается FAQ без придуманной гарантии и с отдельным вопросом о ней.

В конце выпишите предположения, оставшиеся даже после улучшения запроса. Например, язык клиента выбран русским, а публикация ещё не согласована. Укажите это в передаче заказчику: ТЗ управляет созданием черновика, а разрешение на публикацию остаётся отдельным действием. Сохраните версию запроса рядом с результатом, чтобы коллега мог повторить опыт.

### Результат занятия

Два запроса, два ответа и таблица нарушений

### Критерии

- В ТЗ есть данные, ограничения, формат и критерии
- Условие гарантии не выдумано
- Сравнение содержит конкретные примеры нарушений

## Урок 3 из 16 · 1.3 · Эксперимент: одна задача в двух моделях

Код занятия: `CORE-000-M1-L3`.

[← Предыдущий урок: Урок 2 · 1.2 · От простого промпта к хорошему ТЗ](M1.md#lesson-core-000-m1-l2)

[Следующий урок →: Урок 4 · 1.4 · Квиз по критическому мышлению](M1.md#lesson-core-000-m1-l4)

Этот первый эксперимент учит различать наблюдаемый ответ и вывод о качестве. Выберите два доступных инструмента или две явно указанные модели одного сервиса. Запишите дату, название продукта, показанный идентификатор модели и включённые инструменты. Если интерфейс скрывает модель, так и напишите: «версия не раскрыта». Не превращайте торговое название чата в точный идентификатор API.

Для опыта используйте один вход: «Клиент просит назвать стоимость ремонта до диагностики. Регламент: стоимость согласуют после диагностики; предварительная запись возможна; обещать срок без проверки нельзя. Составь ответ до 60 слов, предложи следующий шаг». Заранее определите четыре проверки: нет цены, нет срока, есть объяснение диагностики, есть предложение записи. Только затем запускайте модели в новых чатах с одинаковыми данными.

Сохраните ответы полностью, включая отказ или обрыв. Для каждой проверки поставьте “выполнено” либо “нарушено” и приведите короткое доказательство из ответа. Красивый тон оцените отдельно: он не должен компенсировать выдуманную цену. Измерьте собственное время исправления до готового черновика — оно ближе к рабочим затратам, чем длина ответа.

**Практика.** Выполните по два запуска на инструмент. Отметьте различия между повторами. Ожидаемый результат — четыре сохранённых ответа и узкий вывод: какой вариант лучше справился именно с этим входом при этих настройках. Четыре ответа не доказывают лидерство модели во всех клиентских задачах.

Если доступен только один инструмент, проведите два повтора и подготовьте протокол для будущего сравнения. В отчёте честно обозначьте ограничение; не создавайте вымышленные ответы второй модели. Для следующего модуля сохраните этот тест как начальный пример: позднее вы расширите набор трудными случаями и посчитаете стоимость принятого результата.

### Результат занятия

Протокол четырёх запусков или явно ограниченный протокол одного инструмента

### Критерии

- Проверки определены до запуска
- Есть реальные ответы и сведения о среде
- Вывод ограничен объёмом эксперимента

## Урок 4 из 16 · 1.4 · Квиз по критическому мышлению

Код занятия: `CORE-000-M1-L4`.

[← Предыдущий урок: Урок 3 · 1.3 · Эксперимент: одна задача в двух моделях](M1.md#lesson-core-000-m1-l3)

[Следующий урок →: Урок 5 · 2.1 · Файлы, контекст, RAG — принципиальные отличия](M2.md#lesson-core-000-m2-l1)

Представьте: помощник написал клиенту «мы обязаны вернуть деньги за три дня», приложил ссылку и добавил уверенное объяснение. Здесь есть несколько независимых утверждений: существует норма, она действует в нужной стране, относится к этому договору и действительно задаёт такой срок. Ссылка может вести на существующую страницу, которая не подтверждает ни одного из этих выводов. Оценивать нужно связь конкретного утверждения с доказательством.

Разделяйте факт, вывод и предложение. «В регламенте указано согласование цены» — факт, если строка присутствует. «Клиенты будут больше доверять» — предположение, для которого нужен опыт. «Добавим кнопку записи» — предложение, которое оценивают по цели проекта. Галлюцинацией называют, в частности, уверенно созданное ложное содержание; это не то же самое, что устаревший документ или ваше неверное толкование настоящего источника.

Внутренняя самопроверка модели может обнаружить противоречие, но повторённое утверждение не становится независимым доказательством. Если второй чат пересказал ту же ошибку, у вас два ответа, а не два первоисточника. Полезная проверка обращается к документу, измерению либо ответственному владельцу данных.

**Практика перед квизом.** Разберите три фразы: «по регламенту цена после диагностики»; «это увеличит продажи на 30%»; «стоит добавить запись». Подпишите тип каждой, требуемое доказательство и безопасное действие. Ожидается подтверждение первой по регламенту, отметка “не доказано” для процента и экспериментальное предложение для кнопки.

После квиза перепишите одно неверное утверждение так, чтобы клиент видел границы знания: «Срок возврата требует проверки применимых правил и условий договора». Это не юридическая консультация; учебная цель — распознавать, когда черновик нельзя отправлять без профильной проверки. Объясните свой выбор словами, даже если угадали правильный ответ.

### Результат занятия

Разбор трёх утверждений и результат квиза

### Критерии

- Факты отделены от предположений и предложений
- Существование ссылки не принято за подтверждение
- Указано действие при отсутствии доказательств
