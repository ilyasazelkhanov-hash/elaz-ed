## Четыре части, которые часто путают

Репозиторий — файлы проекта и история их изменений. Он может содержать программу, инструкции, примеры данных и тесты. Скачанный репозиторий ещё не означает работающую программу.

Runtime — программа, которая исполняет код. Здесь это Node.js. Браузер тоже исполняет JavaScript, но окружение у него другое: например, чтение файлов с диска через `node:fs` доступно в Node, а объект `document` относится к браузеру. Ошибка «document is not defined» в Node не означает, что надо установить пакет с названием document.

Зависимости — чужие библиотеки, которые использует проект. `package.json` описывает проект и команды, а lockfile закрепляет разрешённые версии зависимостей. Для проекта с npm и согласованным `package-lock.json` команда `npm ci` воспроизводит установку по lockfile. Она удаляет существующий `node_modules`, поэтому её запускают в нужном каталоге. В нашем маленьком упражнении внешних зависимостей нет: установка не требуется.

Тест — исполняемая проверка ожидаемого поведения. Он не доказывает правильность всей программы: он проверяет только описанные случаи. Успешный запуск тестов нельзя подменять словами агента «должно работать».

Схема: **файлы проекта → подходящий Node → запуск команды → наблюдаемый результат**. Если один шаг сломан, сначала найди его, затем исправляй.

## Учебная задача

В папке `starter` есть расчёт цены ремонта. Мастерская «Маяк» использует вымышленные цены. `quote.mjs` принимает стоимость работы и деталей в целых тенге. При сумме от 10 000 ₸ клиент получает скидку 10% только на работу. Стоимость деталей не уменьшается. Результат округляется до целого тенге.

Пример: работа 8 000, детали 4 000. Общая сумма до скидки — 12 000, значит скидка действует. Работа после скидки стоит 7 200, итог — 11 200. Ответ 10 800 означал бы, что скидка ошибочно применена и к деталям.

Отрицательные суммы, дробные значения и строки отклоняются. Ноль допустим. Такие правила важно определить до обращения к AI: иначе модель может написать аккуратную функцию с другой бизнес-логикой.

## Повтори сам

Открой терминал в корне этого репозитория и выполни:

```bash
node --version
node --test content/ai-academy/drafts/ENG-101/starter/quote.test.mjs
```

Первая команда должна показать версию 24.x. Вторая запускает именно учебные тесты, а не все проверки большого приложения. Прочитай число выполненных проверок и убедись, что нет провалов.

Теперь открой `quote.mjs`, найди умножение стоимости работы на `0.9` и временно замени его на `0.8`. Повтори тесты. Ожидается ошибка сравнения цены: тест замечает неправильную скидку. Верни `0.9` и снова запусти проверки. Сохрани оба результата. Изменяй только учебную копию файла; не трогай исходники приложения.

## Если не получилось

- `node: command not found`: runtime недоступен в текущем терминале. Сначала установи или активируй Node 24 по инструкциям своей среды.
- `Could not find ...quote.test.mjs`: проверь текущую папку командой `pwd` и путь к файлу. Переустановка Node здесь не поможет.
- Один тест упал после изменения `0.9`: это ожидаемая часть упражнения. Сверь фактическую цену с ручным расчётом.
- Все тесты прошли после неверной правки: проверь, сохранился ли файл и тот ли файл ты изменил. Не удаляй утверждения тестов ради зелёного результата.

## Подсказки по очереди

1. Определи, что сломано: запуск Node, поиск файла или само вычисление.
2. Посчитай пример 8 000 + 4 000 вручную. Отдельно выдели стоимость деталей.
3. Запрос к AI: «Объясни расхождение ожидаемой и фактической цены. Сначала предложи проверку гипотезы. Не меняй тест и не переписывай весь проект».

## Что сдать

Короткую заметку с версией Node, командой тестирования, расчётом 11 200 ₸ и объяснением, почему неверная скидка была замечена тестом. Приложи вывод успешного запуска и запуска с намеренной ошибкой. Токены, личные пути и другие чувствительные данные в заметку не включай.

Самопроверка: ты отличаешь файлы от runtime; объясняешь назначение зависимостей; можешь указать проверенный сценарий и границу проверки. Эти тесты не проверяют интерфейс, оплату и серверную базу — в упражнении их нет.

## Урок 2 из 16 · 1.2 · Git и терминал без догадок

Код занятия: `ENG-101-M1-L2`.

[← Предыдущий урок: Урок 1 · 1.1 · Как связаны репозиторий, runtime, зависимости и тесты](M1.md#lesson-eng-101-m1-l1)

[Следующий урок →: Урок 3 · 1.3 · Исходное состояние: сначала измерь](M1.md#lesson-eng-101-m1-l3)

Сначала открой папку проекта в редакторе, затем встроенный терминал. Редактор показывает файлы, терминал выполняет команды в текущем каталоге. Эти места могут различаться. Команда pwd показывает текущую папку, git status показывает состояние репозитория, node --version проверяет доступный runtime. Выполняй их отдельно: так понятно, какой шаг завершился ошибкой. Не копируй чужие абсолютные пути.

Git хранит зафиксированные версии, а рабочая папка содержит текущие изменения. Сохранение файла в редакторе не создаёт коммит. Перед любой правкой прочитай git status; после неё открой git diff. Не запускай git init внутри существующего проекта и не удаляй .git ради устранения сообщения об ошибке. Если Git сообщает, что репозиторий не найден, сначала проверь папку.

В учебной копии создай заметку environment.md с версией Node и командами запуска. Проверь, что в diff появился только этот файл. Новый неотслеживаемый файл виден в status, но обычный git diff его ещё не показывает. Для просмотра открой сам файл; после осознанного git add его содержимое появится в git diff --cached.

### Практика и сдача

Подготовь результат: Заметка о среде и объяснение состояний Git. Сохрани исходное состояние своей учебной копии до изменения. Выполни описанные действия последовательно и запиши наблюдение после каждого существенного шага. Если проверка не прошла, приложи точную команду и объясни следующую проверяемую гипотезу. Не отмечай невыполненные действия как успешные.

### Самопроверка

- Указана текущая папка без чувствительных данных
- Различены сохранение файла и коммит
- Проверен состав добавляемых файлов

### Если застрял

Начни с одного входного примера и ручного ожидания. Затем попроси AI объяснить конкретное расхождение, не выдавая готовое решение вместо твоей попытки. Сверь ответ с файлом и фактическим запуском.

Код занятия: `ENG-101-M1-L3`.

Baseline — зафиксированное состояние до изменения. Без него нельзя уверенно сказать, что тест сломала именно твоя правка. Для нашего starter сначала запусти все восемь тестов цены и сохрани итог. Отдельно запиши версию Node и идентификатор коммита командой git rev-parse HEAD. Номер коммита описывает историю, но не включает несохранённые изменения рабочей папки, поэтому рядом нужен git status.

Перенеси starter в отдельную учебную папку за пределами основного репозитория. Скопируй quote.mjs и quote.test.mjs, сохрани их взаимное расположение. Внешних библиотек здесь нет: npm install не нужен. Выполни node --test quote.test.mjs из новой папки. Такой перенос проверяет, что пример не зависит от случайно установленных библиотек большого приложения.

В отчёте различай «проверки выполнены» и «команды предложены». Запиши фактическое число успешных тестов и код завершения процесса. Если исходные тесты уже падают, сохрани ошибку и исследуй её до изменения бизнес-правила. Иначе новый дефект и старый сбой смешаются. Не исправляй незнакомый большой проект одновременно с настройкой этого маленького упражнения.

## На примере: Разобрать ошибку запуска по слоям

Файлы проекта, среда исполнения и команды проверки — разные части. Среда исполнения здесь означает программу, которая запускает код, например Node.js.

В учебной папке лежит небольшая функция расчёта и её тест. Ошибка запуска не обязательно означает ошибку самой функции.

### Разберём по шагам

1. Проверь текущую папку и версию Node, затем найди точное имя файла теста.
2. Запусти указанную проверку без изменений и сохрани команду, код завершения и полезную строку ошибки.
3. Определи слой проблемы: неправильный путь, неподходящая среда или провал ожидаемого поведения; меняй только найденную причину.
