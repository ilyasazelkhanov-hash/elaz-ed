## Урок 9 из 16 · 3.1 · Frontend, backend, API: минимум терминов

Код занятия: `VC-101-M3-L1`.

[← Предыдущий урок: Урок 8 · 2.4 · Проверка доступности и пользовательского сценария](M2.md#lesson-vc-101-m2-l4)

[Следующий урок →: Урок 10 · 3.2 · Демонстрация генерации сайта в Replit/Lovable](M3.md#lesson-vc-101-m3-l2)

Frontend — код интерфейса, который выполняется в браузере. Он рисует каталог, читает значения полей и реагирует на нажатия. Backend — отдельная программа, обычно на сервере: она принимает запросы, проверяет правила и организует хранение. API — договор об обмене: какие данные отправляются, куда и какой ответ считается успехом.

В нашем учебном продукте backend пока отсутствует. Запись в localStorage остаётся у данного браузерного origin — сочетания схемы, хоста и порта. Другая вкладка того же origin может читать её, а другой браузер или телефон не получит запись автоматически. Данные могут быть очищены пользователем; операции также способны завершиться ошибкой. Это свойства [Web Storage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage), а не доставка заявки.

## Проследите путь данных

Клиент выбирает услугу → React обновляет состояние → обработчик проверяет поля → объект превращается в JSON → браузер сохраняет строку → интерфейс показывает сохранённый объект. Откройте DevTools, раздел Network, и выполните сохранение. Отсутствие запроса к API согласуется с архитектурой. Затем найдите ключ master-request-v1 в Application/Storage. Названия вкладок могут различаться между браузерами.

Для будущего сервера контракт выглядел бы так: POST /api/requests с serviceId, name и contact. Ответ 201 с идентификатором означал бы, что сервер принял создание. Но контракт на бумаге не создаёт endpoint; fetch к несуществующему адресу не заменяет backend.

Практика: нарисуйте два пути — текущий локальный и будущий серверный. Отметьте точку, где каждый может отказать. В серверном пути проверка должна повторяться на сервере: пользователь может обойти браузерную форму и отправить собственный запрос. Браузерная валидация улучшает ввод, но не обеспечивает защиту сервера.

Типичная ошибка — считать переменную окружения во frontend тайным хранилищем. В Vite значения с префиксом VITE_ попадают в клиентский код; ключи и пароли туда не помещают. Итоговая проверка: объясните, почему сообщение «Мастер получил заявку» было бы недостоверным в текущей версии.

## Урок 10 из 16 · 3.2 · Демонстрация генерации сайта в Replit/Lovable

Код занятия: `VC-101-M3-L2`.

[← Предыдущий урок: Урок 9 · 3.1 · Frontend, backend, API: минимум терминов](M3.md#lesson-vc-101-m3-l1)

[Следующий урок →: Урок 11 · 3.3 · Собираем форму, страницу и обработку данных](M3.md#lesson-vc-101-m3-l3)

Название урока перечисляет Replit/Lovable как примеры среды с агентом. Урок не требует подписки и не зависит от расположения кнопок в конкретном продукте: ту же работу можно выполнить в доступном AI-редакторе или вручную в локальном React/Vite проекте. Здесь демонстрируется последовательность действий и ожидаемые файлы, а не запись чужого видео.

Начните с существующего учебного проекта. Прочитайте package.json: scripts подскажет реальные команды запуска и сборки. Для стандартного Vite обычно используются npm run dev и npm run build, но в готовом репозитории сначала проверяют его инструкции. Зависимости берутся из имеющегося lockfile; не просите агента обновлять всё «до последнего».

## Первый ограниченный проход

Передайте агенту PRD, wireframe и список состояний. Запрос: «В текущем проекте реализуй только каталог и выбор услуги. Используй существующие React и CSS. Три serviceId: tap, light, inspect. Кнопка меняет выбранное значение в форме. Не добавляй backend, оплату или пакеты. Сначала покажи план файлов, затем минимальный diff и способ проверки».

Изучите изменения: действительно ли затронуты компонент страницы и стили, нет ли сгенерированных секретов и случайной замены настроек. Запустите приложение и выберите light, затем tap. Форма должна следовать за последним действием. Если выбор только меняет цвет карточки, действие выполнено наполовину.

## Второй проход

Попросите добавить форму и обработчик из следующего урока. Отдельно потребуйте сохранение введённых данных при ошибке. После реализации выполните три конкретных проверки: пустая форма, корректная учебная заявка, обновление страницы. Сохраните скриншоты или краткий журнал фактических результатов. Ответ агента «всё работает» не заменяет запуск.

Если сборка падает, скопируйте точную ошибку и ближайший контекст файла. Попросите найти причину до правки. Ошибка импорта и неверное бизнес-правило требуют разных изменений; общий запрос «почини всё» скрывает разницу.

Типичная ошибка — продолжать генерацию на незапускающейся версии. После каждого небольшого шага нужен работающий результат либо зафиксированная причина отказа. Контрольный результат урока — воспроизводимая история из двух изменений, а не количество сообщений с агентом.

Скриншот локального MVP после реального запроса к учебному серверу. Обрати внимание: запись сохранена, уведомление не отправлялось.

Ниже — самостоятельный пример src/App.jsx для учебного React-проекта. Он использует только React и браузерное хранилище. Примените стили второго модуля или свои. Если приложение уже собрано по макету, перенесите в него обработчик и правила, сохранив доступную разметку.

Обратите внимание на три объекта. Черновик содержит то, что пользователь редактирует. errors хранит объяснения отказов. saved — отдельный снимок успешно записанной заявки. Благодаря разделению изменение черновика не переписывает подтверждение задним числом. В хранилище остаётся только последняя заявка: это явное ограничение демо.

## Выполните лабораторную работу

1. Вставьте пример, запустите проект и сначала сохраните вымышленную заявку с услугой light. Нажмите обновление. Должно остаться подтверждение с теми же данными. Найдите соответствующий JSON в DevTools.
2. Нажмите «Новая заявка», отправьте имя из пробелов и короткий контакт. Вызов trim убирает крайние пробелы до проверки; HTML minLength сам по себе такую бизнес-проверку не заменяет. Исправление не должно требовать повторного ввода всех полей.
3. В DevTools подмените сохранённую строку на некорректный JSON и обновите страницу. Пример проигнорирует нечитаемую запись и покажет пустую форму. Это выбранное поведение учебного прототипа: отметьте его в README, чтобы не обещать восстановление данных.
4. Временно замените localStorage.setItem на throw new Error('Учебный отказ'). Отправьте корректные данные: появится ошибка хранения, успех не появится, ввод сохранится. Верните исходную строку и повторите.
5. Быстро нажмите кнопку дважды. Состояние saving отключает кнопку; короткая задержка в примере нужна только для наблюдения этого состояния. Она не имитирует реальную доставку по сети.

## Что проверить в объекте

serviceId должен принадлежать каталогу, имя — иметь 2–60 символов после trim, контакт — 3–80. При загрузке проверяется та же форма записи. Дата createdAt — момент записи в браузере, а не назначенное время визита. Не добавляйте произвольный HTML из имени через dangerouslySetInnerHTML: текст должен оставаться текстом.

Типичная ошибка — сначала рисовать успех, затем пытаться сохранить. Здесь подтверждение появляется только после завершения setItem. Сдайте работающую страницу и четыре пары «действие → наблюдение»: корректная запись, отказ валидации, перезагрузка, отказ хранилища. Для демо используйте вымышленные контакты.

```jsx
import { useState } from 'react';
import './App.css';

const KEY = 'master-request-v1';
const services = [
  { id: 'tap', title: 'Ремонт смесителя' },
  { id: 'light', title: 'Установка светильника' },
  { id: 'inspect', title: 'Диагностика поломки' },
];
const empty = { serviceId: 'tap', name: '', contact: '' };

function validate(value) {
  const errors = {};
  if (!services.some(s => s.id === value.serviceId))
    errors.serviceId = 'Выберите услугу из списка';
  if (typeof value.name !== 'string' ||
      value.name.trim().length < 2 || value.name.trim().length > 60)
    errors.name = 'Имя: от 2 до 60 символов без крайних пробелов';
  if (typeof value.contact !== 'string' ||
      value.contact.trim().length < 3 || value.contact.trim().length > 80)
    errors.contact = 'Учебный контакт: от 3 до 80 символов';
  return errors;
}

function readSaved() {
  try {
    const value = JSON.parse(localStorage.getItem(KEY) || 'null');
    if (!value || Object.keys(validate(value)).length ||
        typeof value.createdAt !== 'string') return null;
    return value;
  } catch {
    return null; // отсутствующую или нечитаемую запись не восстанавливаем
  }
}

export default function App() {
  const [draft, setDraft] = useState(empty);
  const [saved, setSaved] = useState(readSaved);
  const [status, setStatus] = useState('editing');
  const [errors, setErrors] = useState({});
  const busy = status === 'saving';

  function change(event) {
    const { name, value } = event.target;
    setDraft(previous => ({ ...previous, [name]: value }));
  }

  async function submit(event) {
    event.preventDefault();
    if (busy) return;
    const nextErrors = validate(draft);
    setErrors(nextErrors);
    if (Object.keys(nextErrors).length) return;
    const request = {
      serviceId: draft.serviceId,
      name: draft.name.trim(),
      contact: draft.contact.trim(),
      createdAt: new Date().toISOString(),
    };
    setStatus('saving');
    try {
      // Только учебная задержка, HTTP-запроса здесь нет.
      await new Promise(resolve => setTimeout(resolve, 300));
      localStorage.setItem(KEY, JSON.stringify(request));
      setSaved(request);
      setStatus('success');
    } catch {
      setErrors({ storage: 'Не удалось сохранить. Проверьте настройки браузера и повторите.' });
      setStatus('error');
    }
  }

  return <main>
    <h1>Мастер рядом</h1>
    <p>Учебный прототип. Используйте вымышленные данные.</p>
    <div className="layout">
      <section aria-labelledby="services-heading">
        <h2 id="services-heading">Выберите услугу</h2>
        <div className="cards">{services.map(service =>
          <article key={service.id}>
            <h3>{service.title}</h3>
            <p>Стоимость после уточнения.</p>
            <button type="button" disabled={busy || Boolean(saved)}
              aria-pressed={draft.serviceId === service.id && !saved}
              onClick={() => setDraft(d => ({ ...d, serviceId: service.id }))}>
              Выбрать: {service.title}
            </button>
            {!saved && draft.serviceId === service.id && <p>Выбрано</p>}
          </article>
        )}</div>
      </section>
      <section aria-labelledby="request-heading">
        <h2 id="request-heading">Учебная заявка</h2>
        {saved ? <div>
          <div role="status">
            <p>Сохранено на этом устройстве; мастеру не отправлено.</p>
            <p>{services.find(s => s.id === saved.serviceId)?.title}</p>
            <p>{saved.name}: {saved.contact}</p>
          </div>
          <button type="button" onClick={() => {
            setSaved(null); setDraft(empty); setErrors({}); setStatus('editing');
          }}>Новая заявка</button>
        </div> : <form noValidate onSubmit={submit}>
          <label htmlFor="serviceId">Услуга</label>
          <select id="serviceId" name="serviceId" value={draft.serviceId}
            onChange={change} disabled={busy}
            aria-invalid={Boolean(errors.serviceId)}
            aria-describedby={errors.serviceId ? 'service-error' : undefined}>
            {services.map(s => <option key={s.id} value={s.id}>{s.title}</option>)}
          </select>
          {errors.serviceId && <p id="service-error">{errors.serviceId}</p>}
          <label htmlFor="name">Имя</label>
          <input id="name" name="name" value={draft.name} onChange={change}
            disabled={busy} required maxLength={60}
            aria-invalid={Boolean(errors.name)}
            aria-describedby={errors.name ? 'name-error' : undefined} />
          {errors.name && <p id="name-error">{errors.name}</p>}
          <label htmlFor="contact">Учебный контакт</label>
          <input id="contact" name="contact" value={draft.contact} onChange={change}
            disabled={busy} required maxLength={80}
            aria-invalid={Boolean(errors.contact)}
            aria-describedby={errors.contact ? 'contact-error' : 'contact-hint'} />
          <p id="contact-hint">Например: demo-contact. Не вводите настоящий номер.</p>
          {errors.contact && <p id="contact-error">{errors.contact}</p>}
          <p>Запись только на этом устройстве, без отправки мастеру.</p>
          {errors.storage && <p role="alert">{errors.storage}</p>}
          <button type="submit" disabled={busy}>
            {busy ? 'Сохраняем…' : 'Сохранить учебную заявку'}
          </button>
        </form>}
      </section>
    </div>
  </main>;
}
```

Реальное состояние ошибки локального учебного прототипа, вымышленные данные. Проверь, понятно ли, какое поле исправить и почему.

Баг — воспроизводимое расхождение с согласованным поведением. Неудачный запрос может быть причиной бага, но это разные уровни объяснения. Если PRD требует сохранять выбранную услугу, а код всегда пишет tap, дефект находится в реализации. Если PRD вообще не определяет сохранение, сначала придётся принять продуктовое решение.

Рассмотрите три случая. «После обновления запись исчезает»: проверьте, был ли вызов setItem и читается ли тот же ключ. «После исправления имени форма всё ещё сообщает ошибку»: проверьте, когда очищается errors и не используется ли старый объект. «Хочу, чтобы мастеру пришло сообщение»: это новая серверная возможность, если согласована только локальная версия.

## Отчёт, который помогает исправить код

Запишите среду и точные шаги: открыть чистую страницу, выбрать light, имя «Ая», контакт «demo-contact», сохранить, обновить. Ожидание: восстановилась light. Факт: восстановилась tap. Добавьте одну улику: значение serviceId из Storage. Если в Storage лежит tap, ошибка до записи; если light, но экран показывает tap — ошибка при чтении или отображении. Это сужает поиск лучше любого общего описания.

Практика: намеренно замените serviceId в создаваемом request на 'tap'. Воспроизведите дефект и исправьте только эту строку. Повторите тот же сценарий, затем проверьте ещё одну услугу. Сохраните diff до/после. Работайте в учебной копии, чтобы намеренный дефект не попал в финальную версию.

Когда агент предлагает переписать весь компонент, попросите объяснить связь изменения с уликой. Большой diff не доказывает глубокого исправления и затрудняет проверку. Если предложенная причина не подтверждается, соберите новые данные.

Типичная ошибка — считать исчезновение симптома объяснением причины. Очистка хранилища может скрыть ошибку чтения, но не исправить её. Контрольный результат — краткий баг-репорт, минимальная правка и повтор того же теста с отмеченным результатом.

### Результат занятия

docs/bug-report.md и минимальный исправляющий diff

### Критерии

- Разделены требование, дефект и новая возможность
- Есть улика из Storage
- Повторён исходный сценарий после исправления
