## Урок 13 из 16 · 4.1 · Что такое деплой и домен

Код занятия: `VC-101-M4-L1`.

[← Предыдущий урок: Урок 12 · 3.4 · Как отличать баги от плохого промпта](M3.md#lesson-vc-101-m3-l4)

[Следующий урок →: Урок 14 · 4.2 · Демонстрация публикации и изменений](M4.md#lesson-vc-101-m4-l2)

Деплой — размещение собранной версии в среде, где её смогут открыть пользователи. Для нашего frontend это HTML, CSS и JavaScript. Браузер получает эти файлы по HTTP и выполняет код. Сервер, который раздаёт статические файлы, сам по себе не становится backend приёма заявок.

Vite собирает production-версию командой build из scripts проекта; в стандартной настройке результат оказывается в dist. Команда preview помогает локально проверить собранный результат, но не предназначена для публичного production-сервера. Эти различия описаны в [инструкции Vite по размещению статического сайта](https://vite.dev/guide/static-deploy.html).

Домен — имя, по которому находят ресурс. Покупать отдельное имя для учебного проекта необязательно: достаточно адреса, предоставленного доступным хостингом. HTTPS защищает передачу между браузером и сервером, но не доказывает, что форма действительно отправляет заявку.

## Практика перед публикацией

Прочитайте scripts и выполните штатную сборку в учебном проекте. Найдите каталог результата. Откройте его состав: исходный JSX превратился в подключаемые браузером файлы. Проверьте сборку через preview, используя выведенный терминалом адрес. Не открывайте index.html двойным щелчком как единственный способ проверки: file:// отличается от обычного HTTP-origin.

Сравните localhost и будущий публичный адрес. У них разные origin, поэтому локальная заявка не обязана переноситься. Это ожидаемое поведение, которое важно объяснить пользователю.

Типичная ошибка — загружать папку src вместо результата сборки. Другая — принимать успешное завершение build за проверку формы. Сборка подтверждает возможность собрать код, а пользовательский сценарий проверяется отдельно. Итог урока — найденный артефакт сборки и записанная схема «исходники → сборка → статический хостинг → браузер».

## Простыми словами

Сборка превращает исходники в файлы, которые раздаёт сайт. Preview помогает локально проверить собранную версию, а деплой размещает её на доступном пользователям хостинге. Домен — имя адреса; сам адрес не добавляет серверную обработку формы.

### Один маленький пример

Учебный сайт кружка может открываться через HTTPS и всё равно сохранять заявки только в браузере посетителя. Перенос с localhost на другой адрес также не переносит локальную запись автоматически. Нужно отдельно проверить внешний вид, форму и честность подтверждения.

### Повтори на учебной копии

1. В учебном проекте прочитай scripts в package.json. Если там определён build, выполни npm run build и найди фактический каталог результата; в стандартном Vite это dist.
2. Если определён preview, запусти npm run preview и открой адрес, который вывел терминал. Не заменяй эту проверку двойным щелчком по index.html.
3. Запиши команду и каталог в docs/deploy-plan.md. Нарисуй путь от исходников до браузера и отметь, что изменится для localStorage при другом адресе.

### Наблюдаемый результат

Будет найденный артефакт сборки и локально проверенный HTTP-адрес этой версии, без заявления о состоявшейся публичной публикации.

### Частая ошибка

Загрузить на хостинг только src или считать успешную сборку проверкой всех пользовательских действий.

### Объясни своими словами

- Проверяю ли я именно собранные файлы?
- Могу ли я объяснить разницу между preview и публичным сайтом?

Пример вымышленный. В итоговую работу приложи свои входные данные, фактический результат и проверку.

## Урок 14 из 16 · 4.2 · Демонстрация публикации и изменений

Код занятия: `VC-101-M4-L2`.

[← Предыдущий урок: Урок 13 · 4.1 · Что такое деплой и домен](M4.md#lesson-vc-101-m4-l1)

[Следующий урок →: Урок 15 · 4.3 · Деплоим и проводим smoke-test](M4.md#lesson-vc-101-m4-l3)

Для практики используйте уже доступную вам площадку статического хостинга. Урок не требует покупки домена, передачи ключей или подключения облачного backend. Если доступа к публикации пока нет, выполните весь локальный прогон собранной версии и отметьте публичную ссылку как незавершённый пункт: не выдавайте localhost за опубликованный сайт.

Сначала сохраните рабочую версию и запишите её идентификатор: commit, если используете Git, либо номер архивной копии. В Git история доступна через git log; достаточно git log -1 --oneline, чтобы найти последнюю запись. Проверьте, нет ли незакоммиченных изменений: иначе один commit не описывает всё содержимое текущей сборки.

## Выполните один управляемый выпуск

1. Запустите штатную build-команду и проверьте её успешное завершение.
2. В существующей панели хостинга выберите размещение статических файлов. Если площадка собирает из репозитория, укажите реальную команду и каталог результата; при ручной загрузке передайте содержимое собранного каталога.
3. Дождитесь завершения операции и откройте выданный адрес в отдельном браузерном контексте. Проверьте заголовок, стили и учебную заявку.
4. Измените один видимый текст, например уточните подпись локального хранения. Повторите сборку и выпуск. Откройте адрес заново и найдите новый текст.
5. Сохраните таблицу: версия, изменение, команда, адрес, результат smoke-test. Если обновление не видно, сначала сравните версию и загруженные ресурсы, затем исследуйте кэш.

При размещении в подпапке проверьте настройку base согласно инструкции Vite: неверный путь к ресурсам может дать пустую страницу, хотя HTML загрузился. Не меняйте base наугад, если сайт размещён в корне.

Типичная ошибка — редактировать собранный файл на сервере и забывать исходники. Следующая сборка затрёт такую правку. Контрольный результат — два прослеживаемых выпуска одного приложения и объяснение, как вернуться к предыдущему рабочему артефакту средствами выбранной площадки.

Проведите учебный откат: восстановите предыдущий артефакт через предусмотренную площадкой историю выпусков или повторную загрузку его файлов. Проверьте возврат прежнего текста. Затем снова разместите исправленную версию. Такая проверка учит отличать редактирование исходников от выбора того, что сейчас обслуживает публичный адрес. Если площадка не хранит историю, сохранённый архив сборки становится вашим материалом для возврата.

## Простыми словами

Выпуск связывает конкретную версию исходников с размещённой сборкой и проверкой поведения. Чтобы безопасно показать изменение, нужно знать, какой артефакт был раньше и как его вернуть. Редактирование текста в исходниках само по себе ещё не обновляет доступный сайт.

### Один маленький пример

У учебного кружка в первой сборке подпись говорит «локальная запись», а во второй уточняет, что организатор не уведомлён. Проверяющий должен открыть нужный адрес и увидеть разницу. Если доступа к хостингу нет, обе сборки можно проверить локально, обозначив публикацию как незавершённую.

### Повтори на учебной копии

1. Сохрани рабочую версию и её идентификатор. При использовании Git команда git log -1 --oneline показывает последнюю запись, но отдельно проверь незакоммиченные изменения.
2. Выполни штатную сборку и размещение на уже доступной площадке либо честный локальный preview. Измени одну заметную подпись и повтори тот же путь.
3. В docs/releases.md запиши две версии, адреса и результаты проверок. Испытай возврат предыдущего артефакта предусмотренным площадкой способом или локальной сохранённой копией.

### Наблюдаемый результат

Получится история двух управляемых выпусков и понятный путь возврата, с точным статусом публичного доступа.

### Частая ошибка

Править собранный файл отдельно от исходников: следующая сборка может затереть такую правку.

### Объясни своими словами

- Знаю ли я, какую версию сейчас открываю?
- Есть ли проверенный материал для возврата к предыдущему состоянию?

Пример вымышленный. В итоговую работу приложи свои входные данные, фактический результат и проверку.

Smoke-test — короткий набор проверок, который быстро обнаруживает поломку основного сценария. Он не заменяет все испытания. Для нашей мастерской достаточно убедиться, что страница загрузилась, выбранная услуга дошла до записи, ошибка не потеряла ввод, а обновление восстановило последнюю заявку.

Сначала выполните тест вручную на адресе production-сборки. Откройте чистый браузерный контекст, чтобы предыдущая запись не скрывала форму. Проверьте R1 из PRD: light, имя «Ая», контакт «demo-contact», сохранение, правильное подтверждение. Затем обновите страницу и сравните поля. После «Новой заявки» введите имя из пробелов: успех появляться не должен. Отдельно повторите клавиатурный путь и проверку ширины 360 px.

## Добавьте один автоматический тест

Если Playwright уже используется в учебном проекте, поместите пример ниже в его каталог тестов. Предварительно запустите production-preview на указанном адресе либо используйте существующий webServer в конфигурации. В команде запуска и адресе учитывайте настройки проекта. Если Playwright отсутствует, ручной протокол остаётся обязательным, а автоматизация — отдельным шагом с установкой по официальной инструкции; не изображайте выполненный запуск.

Тест использует getByLabel и getByRole: он ищет интерфейс так, как его различает пользователь. Условия expect ожидают нужного состояния, поэтому фиксированная пауза после нажатия не требуется. Если подпись кнопки меняется, тест покажет, какое пользовательское соглашение изменилось; бессмысленный селектор по случайному CSS-классу даёт меньше пользы.

## Испытайте полезность проверки

В учебной копии замените serviceId на постоянный tap, как в предыдущем модуле. Тест для light должен упасть. Верните правильный код и повторите тот же тест. Так вы проверите, что сценарий ловит реальное нарушение, а не просто открывает страницу.

Сохраните дату, адрес версии, браузер и результат каждого пункта. При отказе приложите конкретное расхождение; не ставьте отметку «пройдено» за одну только загрузку.

Типичная ошибка — запускать тест только на dev-сервере, а выпускать другую сборку. Финальная проверка должна относиться к тому артефакту и адресу, которые увидит проверяющий. Перед защитой убедитесь, что намеренно внесённый дефект удалён.

Если тест падает, сохраните сообщение ожидания и снимок страницы: они помогут отличить отсутствие нужной кнопки от неверного значения в подтверждении.

```javascript
test('учебная заявка сохраняет выбранную услугу', async ({ page }) => {
  // Замените порт, если preview проекта использует другой.
  await page.goto('http://localhost:4173/');
  await page.getByRole('button', {
    name: 'Выбрать: Установка светильника', exact: true,
  }).click();
  await page.getByLabel('Имя', { exact: true }).fill('Ая');
  await page.getByLabel('Учебный контакт', { exact: true }).fill('demo-contact');
  await page.getByRole('button', {
    name: 'Сохранить учебную заявку', exact: true,
  }).click();

  const confirmation = page.getByRole('status');
  await expect(confirmation).toContainText('мастеру не отправлено');
  await expect(confirmation).toContainText('Установка светильника');
  await expect(confirmation).toContainText('demo-contact');
  await page.reload();
  await expect(page.getByRole('status')).toContainText('Установка светильника');
});
```

## Простыми словами

Smoke-test — короткая проверка, что главная задача пользователя работает в выпускаемой версии. Он не доказывает отсутствие всех ошибок. Полезный тест должен заметить заранее известный дефект, а не просто открыть страницу и завершиться успешно.

### Один маленький пример

Для учебного кружка недостаточно увидеть каталог: нужно выбрать занятие, сохранить вымышленный контакт и проверить восстановление после обновления. Если тест не заметит подменённое название занятия, он пропускает важную часть пользовательского обещания. Проверять следует тот адрес и сборку, которые получит проверяющий.

### Повтори на учебной копии

1. Открой production-preview своей версии в чистом браузерном контексте. Выполни успешный сценарий мастерской и сравни выбранную услугу, контакт и восстановление записи.
2. Проверь ошибочный ввод, клавиатуру и узкую ширину. В учебной копии повтори намеренный serviceId-дефект и убедись, что протокол действительно его обнаруживает.
3. Верни корректный код и повтори проверки. В docs/smoke-test.md укажи версию, адрес, браузер и фактический результат; Playwright-пример запускай только после настройки существующего тестового окружения.

### Наблюдаемый результат

Будет короткий проверяемый протокол, который различает рабочую и намеренно сломанную версию.

### Частая ошибка

Тестировать только dev-сервер, а показывать другую сборку без повторной проверки.

### Объясни своими словами

- Относится ли результат к показываемой версии?
- Есть ли конкретный дефект, который моя проверка действительно ловит?

Пример вымышленный. В итоговую работу приложи свои входные данные, фактический результат и проверку.

## Урок 16 из 16 · 4.4 · Защита: показать ценность за 3 минуты

Это последний урок курса. Проверь итоговую работу по критериям; чтение страницы само по себе не даёт зачёт.

Трёхминутное демо — рассказ с доказательствами. Проверяющий должен понять задачу, увидеть результат и оценить границы. Не тратьте первую минуту на список AI-инструментов: клиент пришёл оставить заявку, а не изучать процесс генерации.

Подготовьте README с назначением, командами запуска и сборки, ссылкой на доступную версию, местом хранения и ограничениями. Укажите проверенные сценарии и один известный недостаток. Если публичного адреса пока нет, напишите это прямо и покажите production-preview; требование публикации остаётся невыполненным до появления ссылки.

## Репетиция на 180 секунд

Первые 30 секунд: назовите клиента и работу — оставить понятную заявку с телефона. Следующие 60: выберите светильник, заполните учебные данные и покажите подтверждение с выбранной услугой. Ещё 30: обновите страницу, продемонстрируйте восстановление и объясните, почему другой телефон не получит запись. Следующие 30: покажите отказ валидации и сохранение введённых данных. Последние 30: предъявите PRD, результаты smoke-test и назовите следующий необходимый шаг — серверный приём с подтверждением сохранения и уведомлением оператора.

Если нужно открыть DevTools, заранее подготовьте нужную вкладку. Не подменяйте живой сценарий скриншотом «успеха»: снимок полезен как приложение, но не доказывает текущее поведение. При сбое спокойно покажите шаги воспроизведения и зафиксированную версию.

Практика: запишите одну репетицию или проведите её перед другим участником. Попросите его ответить на три вопроса: кто пользуется продуктом, куда попадают данные, что нужно сделать для реального приёма. Если ответы неверны, исправьте объяснение или интерфейс.

Типичная ошибка — назвать прототип готовой системой записи. Здесь защищается работающий, проверенный frontend с локальной учебной заявкой. Чёткое объяснение ограничения — часть технической самостоятельности. Сдайте README, артефакты модулей и демонстрацию, в которой каждое обещание можно сопоставить с наблюдением.

3. Проведи репетицию и попроси согласившегося человека объяснить, куда ушли данные и что нужно для реального приёма. Если слушателя нет, отметь авторскую репетицию; затем исправь неясные подписи или рассказ.
