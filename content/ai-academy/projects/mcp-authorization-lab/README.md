# ENG-201: авторизация удалённого MCP без настоящих токенов

Учебная цель: объяснить, почему подпись токена, его назначение, разрешённое действие и происхождение браузерного запроса проверяют отдельно. Это **авторская офлайн-модель политики**, а не MCP-сервер, OAuth-клиент, JWT-валидатор или готовая защита production.

## Запуск

Нужен Node.js 24. Установка пакетов, аккаунт, сеть и платный API не нужны:

```sh
node --test policy.test.mjs
node demo.mjs
```

Демонстрация печатает семь JSON-строк: один разрешённый учебный случай и шесть отказов. В каждой есть `synthetic: true`, код случая, решение, причина и список пройденных проверок. Она ничего не отправляет и не записывает. Домены `.example.test`, время и все данные вымышлены.

## Где проходит граница доверия

В рабочей системе недоверенный bearer-токен сначала попадает в доверенный адаптер: проверку JWT библиотекой либо обращение к доверенному introspection endpoint. Адаптер проверяет подпись/активность, доверенный issuer, допустимые алгоритмы, ключи и срок действия. Проверки audience и полномочий также обязательны. Только после этого сервис получает проверенные claims и принимает решение для конкретного ресурса и операции.

Здесь этого адаптера **нет**. `fixtures.mjs` передаёт строку `verificationOutcome: 'verified'` как заданное автором условие задачи. Любой, кто может менять вход функции, может написать эту строку сам. Она **не доказывает подпись или личность**. Никогда не принимай такой флаг из HTTP-запроса и не используй `evaluatePolicy` как middleware аутентификации. Отрицательный случай `failed` моделирует отказ адаптера, но не проверяет криптографию.

`policy.mjs` разбирает следующий этап:

1. Проверяет конфигурацию и форму учебных данных. При неизвестном исходе проверки отказывает.
2. Сравнивает issuer (`iss`) точно с доверенной настройкой, без нормализации URL.
3. Ищет точное назначение сервера в audience (`aud`), строке или массиве строк. Токен соседнего сервиса не подходит, даже если подпись верна.
4. Проверяет `exp` и необязательный `nbf` относительно явно переданного времени в секундах Unix. В момент `exp` уже отказывает; в момент `nbf` уже допускает.
5. Разбирает scope как разделённые пробелом имена полномочий. `notes:read:any` не равен `notes:read`. Если нужно несколько scope, требуются все.
6. При включённой политике Origin принимает только разрешённый точный origin. Здесь такая политика требует и наличия заголовка. Это намеренно строгий выбор лаборатории, а не универсальное требование для каждого небраузерного MCP-клиента. Origin не является доказательством личности: небраузерный клиент способен его подставить.

Session ID не участвует в решении. Список `checks` показывает только успешно пройденные стадии; отказ на следующей стадии не означает, что остальные были проверены. Вывод не содержит исходных claims и токенов.

## Практика: объясни каждый отказ

Перед запуском предскажи исход, затем сравни с фактической строкой demo:

- Токен от чужого issuer, но с нужным audience.
- Верный issuer, но назначение другого сервера.
- Scope с похожим названием вместо нужного.
- Срок истёк ровно сейчас.
- Неуспешная проверка токена и одновременно присутствующий session ID.
- Неверный Origin при остальных корректных условиях.

Сделай в отдельной копии две доработки: потребуй одновременно `notes:read` и `notes:export`; добавь второй разрешённый origin. Для каждой напиши разрешённый и запрещённый случай. Не меняй исходные отрицательные тесты так, чтобы они начинали принимать опасный ввод.

Затем сравни два случая: `aud` содержит ровно нужный ресурс внутри массива; `aud` содержит только похожий URL с добавленным `/`. Объясни, почему один проходит, а другой нет. Назначение в конфигурации нужно согласовать с реальным authorization server; его нельзя угадывать или ослаблять до общего `api`.

### Критерии сдачи

- Сохрани фактические результаты тестов и семь строк demo без секретов.
- Покажи свои четыре новых теста, изменение политики и ожидаемый исход каждого.
- Нарисуй путь «недоверенный токен → доверенный адаптер → проверенные claims → политика операции» и отметь, какой этап здесь отсутствует.
- Объясни, почему `verificationOutcome`, Origin и session ID не являются самостоятельными удостоверениями личности.
- Назови минимум три непроверенных свойства будущей сетевой реализации. Не объявляй их выполненными по результату этого fixture.

## Версии и перенос в реальный проект

Проверено по официальному руководству 12 ноября 2026 года. Контекст руководства: **MCP 2026-07-28**. Это не требование заменить версию в старом stdio-примере без изменения обмена.

- OAuth-поток руководства относится к **HTTP-транспорту**. Локальный stdio получает необходимые credentials из среды или встроенных библиотек. Эта лаборатория не добавляет OAuth в существующий stdio fixture.
- Для новых реализаций руководство рекомендует **Client ID Metadata Documents (CIMD)**. **Dynamic Client Registration (DCR)** помечен deprecated и остаётся для совместимости. Клиент регистрируется у authorization server; ресурсный MCP-сервер не должен самостоятельно изобретать CIMD/DCR. Поддержка зависит от выбранного клиента и провайдера.
- Для TypeScript `expectedResource` в `@modelcontextprotocol/express` требует **2.0.2 или новее**; прежние версии игнорируют параметр. Он проверяет ресурс, который сообщил адаптер, а не сам bearer-токен. Поэтому `audience` в `jwtVerify` нельзя убирать. Одного обновления пакета недостаточно: закрепи и проверь совместимые версии SDK, адаптера и провайдера.
- В редакции 2026-07-28 нет MCP-сессий. Сервер только этой редакции игнорирует `Mcp-Session-Id`. При поддержке старых клиентов session ID также нельзя принимать за аутентификацию.
- Строка версии протокола, версия SDK и версия этой лаборатории описывают разные вещи. Здесь SDK вообще не установлен, сетевой обмен не реализован.

## Ограничения

Нет проверки JWT-подписей, алгоритмов и ключей, JWKS, discovery/PRM, redirect URI, PKCE, CIMD/DCR, HTTP, TLS, challenge-ответов, rate limiting и реального субъекта/ролей. Не реализована полная спецификация MCP или OAuth. Код принимает обычные объекты упражнения, а не атакующий JavaScript с getters/proxies. Учебный формат дат ограничен неотрицательными целыми секундами и не допускает clock skew; это осознанное упрощение, а не универсальная реализация JWT NumericDate. Нет проверки совместимости с внешним host/SDK. Настоящие токены, секреты, endpoint и документы в упражнение не вставляют.
