# Инструкции для AI и разработчиков

Это переносимый клиентский проект. Сначала прочитайте `README.md`, `app.config.json`, `brand.config.json`, `src/platform/contracts.ts`, `src/platform/config.ts` и соответствующий сценарий в `docs/`. Реальное состояние реализации и проверок уточняйте по коду и отчётам, а не по рекламному описанию.

## Правила изменений

- Сохраняйте самостоятельность проекта: никаких импортов из родительского checkout, мастер-папки или соседнего клиента.
- Бренд меняйте через `brand.config.json`, возможности — через `app.config.json`; зависимости модулей задаются в реестре. Изменения контрактов согласуйте между фронтендом и сервером.
- Перед изменением оформления читайте `docs/VISUAL-DESIGN.md`. Участник использует мобильный интерфейс, управление — широкую рабочую область. Правила экранов участника находятся в `src/experience.css`; не добавляйте рекламный декор вместо полезных действий.
- Для каждого клиента используйте отдельные Supabase-проект, бота, домен, окружение и резервные копии. Не переносите клиентские данные в мастер.
- Не помещайте bot token, service role, quiz answer keys или приватные файлы во фронтенд, `public`, контент, `VITE_*`, лог или коммит. `.env.example` содержит только заглушки.
- Не считайте UI-проверку защитой. Право, actor, модуль, цена, баланс, лимит, награда и переход статуса проверяются сервером. Клиентские payload не являются источником доверия.
- Обновления, генерацию и синхронизацию сначала проверяйте в новой временной папке. `update` и `sync-og` по умолчанию только строят отчёт. Не переписывайте пользовательский конфиг/контент и не подменяйте SHA-базу для сокрытия конфликтов.
- Миграции, уже применённые у клиента, не редактируйте задним числом. Изменение схемы оформляйте новой миграцией. Таблицы пакета имеют префикс `az_`.
- Не запускайте публикацию, реальные платежи, отправку сообщений или команды облачной БД, если задача этого не предусматривает. Локальные проверки и исправления выполняйте самостоятельно в рамках задачи.
- Не создавайте фиктивные ответы API или зелёные тесты вместо исправления. Демо остаётся явно отмеченным демо.

## Проверка результата

Запускайте относящиеся к изменению проверки. Перед заявлением о полной готовности выполните `npm test`, `npm run build`, проверьте мобильный интерфейс и повторите затронутый сценарий. Для генератора: `node --experimental-strip-types --test tests/generator.test.mjs`. Для БД, Telegram, OIDC, webhook и внешних интеграций укажите отдельно, какие локальные/стендовые проверки действительно выполнены. Не называйте локальную имитацию проверкой production.

Отчёт должен содержать изменённое поведение, команды и результаты проверок, оставшиеся ограничения. Никогда не публикуйте секретные значения. Не коммитьте и не отправляйте изменения, если задача этого не требует.
