# Обновить клиентскую поставку

Генератор не выполняет Git merge и не решает бизнес-конфликты. Он сравнивает SHA-256 файлов с `.platform-kit.json`. Мастер является источником обновления; клиент и его бренд остаются самостоятельными.

## Построить отчёт

Создайте резервную копию клиента и базы. Запустите из мастера:

```sh
node scripts/client.mjs update --out ../north-club
```

Либо из клиента укажите источник:

```sh
node scripts/client.mjs update --source ../Azelkhanov-master --out .
```

Второй вариант требует отдельного источника: клиент не обновляет сам себя. Команда без `--apply` не записывает файлы или базовый манифест.

| Поле отчёта | Что означает | Действие |
|---|---|---|
| added | Файла ещё нет | Будет добавлен при apply |
| updated | Локальный файл совпал с базой; в мастере новая версия | Будет обновлён при apply |
| unchanged | Содержимое уже совпадает | Записи не требуется |
| conflicts | Локальное изменение, неизвестный файл или локальное удаление | Сохранится; нужен ручной diff |
| protected | Конфиг, зависимости, контент или существующая миграция | Сохранится; нужен ручной перенос |
| removedUpstream | Ранее поставленный файл отсутствует в источнике | Сохранится; оцените удаление вручную |
| written | Реально записанные файлы | Заполняется только при apply |

Новая миграция может быть добавлена как новый файл; существующая не перезаписывается. Скрипт не применяет миграции к БД.

## Применить проверенные изменения

```sh
node scripts/client.mjs update --out ../north-club --apply
```

Скрипт повторно проверяет файл непосредственно перед записью. SHA-база обновляется после записи безопасных файлов; для конфликтных и защищённых файлов остаётся предыдущая база. Существующий неизвестный файл не становится управляемым только потому, что совпал с мастером. Удалений нет. Полного транзакционного отката всех файлов при аппаратном/файловом сбое нет: сохраните backup и повторите отчёт после сбоя.

Перенесите изменения `package.json`/lock, app/brand конфигов и локального контента вручную. Если вручную объединённый код отличается от исходной базы, следующие обновления продолжат показывать конфликт — это ожидаемо. Не подменяйте хеш, чтобы принудительно разрешить перезапись. Для намеренного перехода на чистую upstream-версию сохраните локальную копию, проверьте diff и задокументируйте ручной перенос.

Установите зависимости при их изменении, выполните тесты и build в клиенте, затем проверки на стенде. Обновите отдельный серверный конфиг и примените новые миграции только по плану релиза. Переводите production после подтверждения совместимости.

## Границы упаковки

Переносятся только перечисленные в скрипте корневые файлы и каталоги `src`, `content`, `public`, `server`, `supabase`, `scripts`, `tests`, `docs`. Не переносятся `.git`, зависимости, сборки, uploads, backup, export, клиентские папки, `.env` кроме `.env.example`, известные секретные/бинарные DB-файлы, CSV и лог-файлы. Каталог с `.platform-kit.json` исключается при рекурсивном обходе. Symlink/junction и небезопасные manifest-пути вызывают отказ.

Это файловая allowlist и фильтры имён, а не универсальная проверка содержимого на PII/секреты. Не храните реальные клиентские записи или ключи внутри разрешённых исходников, каталога контента, public или `.env.example`. Перед поставкой проверьте diff и состав архива. Для демонстраций используйте обезличенные вымышленные записи.
