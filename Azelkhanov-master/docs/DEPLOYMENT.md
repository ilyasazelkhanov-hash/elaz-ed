# Развернуть отдельную установку

Эта инструкция описывает последовательность работ. Она не означает, что облачная установка, Telegram и платежи уже проверены. Точные переменные, provisioning и ограничения сверяйте с `server/`, `supabase/` и `docs/BACKEND-REPORT.md` текущей версии.

## Подготовить окружение

Создайте отдельные Supabase-проект, Telegram-бота, домен и frontend-проект заказчика. Выберите регион, тариф и сроки хранения по требованиям заказчика. Не используйте в новой установке проект, ключи, webhook или домен мастера/другого клиента.

Сгенерируйте клиент, установите пакеты, выполните тесты и сборку. В клиентском `.env.example` генератор задаёт `VITE_DEMO=false`. Перенесите только необходимые публичные параметры в окружение frontend:

```dotenv
VITE_API_URL=https://PROJECT_REF.supabase.co/functions/v1/master-api
VITE_DEMO=false
```

`PROJECT_REF` здесь заглушка. Адаптер добавляет версию маршрута к API base; сверьте финальный URL в сетевой панели. При `/api` нужен реально настроенный reverse proxy. `vercel.json` поставляет статический frontend и SPA fallback; он сам по себе не создаёт серверный API и не настраивает Supabase.

## Подключить сервер

1. Свяжите Supabase CLI с проектом заказчика. Перед командами миграции проверьте выбранный project reference. Примените миграции из этой поставки сначала на стенде, затем по процедуре заказчика. Старые применённые миграции не меняйте.
2. Задайте серверные секреты через защищённый интерфейс платформы. Пример набора имён ниже; реальные значения не сохраняйте в этом документе.
3. Разверните edge function из `supabase/functions/master-api`. Используйте политику `verify_jwt` из конфигурации этой версии: Telegram и браузерная сессия проверяются сервером приложения. Это не разрешение на публичные административные операции.
4. Загрузите конфигурацию и контент через предусмотренный сервером административный/provisioning сценарий. Синхронизируйте `app.config.json` с серверным `az_settings`, проверьте начального владельца, приватные ответы викторин и ограничения модулей. Не выдавайте service role браузеру для загрузки seed.
5. Настройте отдельное приватное файловое хранилище и права. Проверьте подписанную выдачу файлов и отказ чужому участнику.

```dotenv
# Только сервер. Значения — заглушки, не рабочие ключи.
SUPABASE_URL=https://PROJECT_REF.supabase.co
SUPABASE_SERVICE_ROLE_KEY=REPLACE_IN_SECRET_STORE
BOT_TOKEN=REPLACE_IN_SECRET_STORE
APP_URL=https://CLIENT_DOMAIN
ADMIN_TELEGRAM_IDS=REPLACE_WITH_OWNER_ID
OIDC_CLIENT_ID=REPLACE_IN_SECRET_STORE
OIDC_CLIENT_SECRET=REPLACE_IN_SECRET_STORE
CRON_SECRET=REPLACE_IN_SECRET_STORE
INTEGRATION_WEBHOOK_SECRET=REPLACE_IN_SECRET_STORE
```

Платформа может передавать часть `SUPABASE_*` автоматически. Не дублируйте/переименовывайте переменные, пока не сверили чтение переменных в коде. Параметры cookie session, CORS и webhook secret уточняйте по серверной реализации.

## Настроить Telegram и фоновые операции

Настройте Mini App URL, разрешённый домен входа и callback URI для фактического production-домена. Browser OIDC с cookie требует подходящего same-origin reverse proxy и корректных cookie/CSRF; одной внешней ссылки на функцию недостаточно. Настройте Bot API webhook с секретом и точным endpoint из серверного кода.

Подключите вызов worker/cron по серверной документации. Проверьте доставку, повторы после временного отказа, тихие часы, часовой пояс и отказавшегося от уведомлений участника. Не оставляйте задачу рассылки на незавершённом промисе frontend.

Для цифровых покупок в Telegram пройдите отдельную проверку Stars: создание invoice, pre-checkout, подтверждение, повторный webhook, возврат и выдача/отзыв доступа. Платёжная интеграция считается принятой только после этих проверок на стенде.

## Выпустить frontend и принять

В проекте хостинга задайте каталог клиента как корень, `npm run build` и `dist`. Укажите production env, пересоберите и проверьте, что демо явно выключено. Настройте HTTPS, домен, API и callback. Проверьте состояние service function и БД отдельно от статуса frontend deploy.

В Telegram выполните вход участника и владельца, одну публикацию, начисление с повтором, запись на последнее место, погашение купона, действие запрещённой роли и выключенного модуля. Выполните применимые проверки из `LIMITS.md`. Запишите версии, project reference без ключей, результаты и ответственных в `DELIVERY.md`.

## Особенности OG

Копия OG использует `src/platform-kit`, `server/platform-kit` и `supabase/functions/az-master-api`; таблицы имеют префикс `az_`. `sync-og` не меняет глобальный `supabase/config.toml`: отдельно добавьте конфигурацию функции с фактическим именем и проверьте её режим JWT. Настройте API base копии на её функцию, зависимости root-проекта (включая Three.js и QR-пакет из текущего master package.json), маршрут и `App` props `{ brand, config, apiBase, embedded }`. Бот, роли, миграции и данные требуют собственной проверки совместимости с OG. Не запускайте миграции только потому, что файлы скопированы.

## Подготовить API proxy автоматически

node scripts/configure-hosting.mjs --api https://PROJECT.supabase.co/functions/v1/master-api

Команда меняет только локальный vercel.json. Серверу также нужны WEBHOOK_SECRET для отдельного standalone-бота, API_PUBLIC_PATH=/api и при необходимости ADMIN_RETURN_PATH=/admin. Для OG используйте его PLATFORM-KIT.md и оставляйте единый api/webhook. Provisioning может читать server/rules.example.json через --rules.
